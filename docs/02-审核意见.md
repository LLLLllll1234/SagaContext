## 0. 总体判断

报告的**事实核查质量高**：对 OpenViking Context Assembler 的三条核心"缺口"判断在源码上全部成立，许可证、memsearch RRF、LongMemEval-V2 数字等也均属实。路线 A（独立 Gateway）的边界划分清晰，`[TARGET]/[VERIFY]` 的诚实标注值得保留。

但报告存在**三类需要在立项前解决的问题**：

1. **竞品盲区**：漏掉了至少两个与 SagaContext 定位高度重叠的项目——`claude-mem`（85k+ stars，已跨 Claude Code/Codex/OpenClaw/Gemini/Copilot 共享记忆，服务端已有事件级溯源表）和 `benediktkraus/openviking-hooks`（现名 dreviho，**已经在 OpenViking 之上做了 hybrid search + RRF + 多 scope + MMR + 时间衰减 + citations，覆盖 Claude Code / Codex / Gemini CLI / OpenClaw**）。后者几乎就是路线 A 的既有实现——源码核对显示它做得粗糙（RRF 分数算完即弃、单查询、无评测），但"有人先做了"这一事实必须写进报告（两者源码级对照见附录 A）。
2. **"主创新点"站不住**：TypedQuery-aware Weighted RRF 在方法上就是 RAG-Fusion（2024）+ Weighted RRF（已有多篇论文与开源实现，含按查询类型调权重的版本）。它可以是工程特性，不能是主创新点。
3. **主基准选错域**：LongMemEval-V2 的 haystack 是 **web-agent 轨迹**（web / enterprise 两个领域），不是 coding 任务；用它当 coding agent 记忆系统的主基准是领域错配。已有面向 coding 的多会话记忆基准（MemoryCode）和代码记忆检索基准（LongMemCode）可用。

另有一个**战略风险**：报告识别的 OpenViking 缺口在代码上极小（`expansion.py` 返回 `List[str]`、`gather.py` 的 `dedupe_keep_best` 取最高分，合计约 30 行），上游一个 PR 就能填平。如果 SagaContext 把它当主创新，项目的差异化会随上游一次合并消失。建议把"TypedQuery 保真 + RRF 累加"作为向上游贡献的 PR，把 SagaContext 的独立价值放到上游不会做、且社区已明确提出需求的方向——**记忆证据链（provenance）+ 跨宿主统一评测协议**。

## 2. 报告遗漏的竞品与先例（按威胁程度排序）

### 2.1 `benediktkraus/openviking-hooks`（已改名 **dreviho**，Apache-2.0）— **最直接的重叠**
- Fork 自 `Castor6/openviking-plugins`，在 OpenViking 之上实现：**Hybrid search（semantic + grep + RRF merge）→ 5-scope（按 CWD）→ 7 维排序 → MMR 去冗 → 时间衰减 → 压缩 → citations**；capture 侧有 substance filter、内容合并（>0.85 追加而非重复）、auto-link、`/sessions/{id}/used` 反馈。
- 支持 **Claude Code、Codex、Gemini CLI、OpenClaw 共享同一记忆池**。
- 已作为 OpenClaw 自定义 ContextEngine 提交（openclaw/openclaw#83759，被标 P3），在 openai/codex Discussion #23364 有公告。
- **源码级核对结论（详见附录 A）：** 单开发者、v0.1.5、最后提交 2026-05-29、约 5.7k 行 JS/TS、无评测。它**完全绕开 OpenViking 的 Context Assembler**（直接调 `/search/find` 列表模式），在 hook 进程内重做排序；**只有单查询**，无 TypedQuery/intent；其 RRF 实际是摆设——`rrfMerge` 算出的 `rrfScore` 随后被 `postProcess`/`getRankingBreakdown` 忽略，排序仍按原始 `item.score`（grep 命中用 `1/(i+1)` 伪分数，第一条直接得 1.0）。
- **对 SagaContext 的影响：** "Gateway 在 OpenViking 边界上做 RRF + 作用域 + 多宿主"这条路线已有人做，且做得粗糙——这既是威胁也是机会。SagaContext 的增量必须是它没有的：TypedQuery/priority 保真、真正生效且可分解的融合、证据链、统一评测协议。建议将其列入 §4 对照并作为评测基线之一。

### 2.2 `thedotmack/claude-mem`（Apache-2.0，~85k stars，v13.24.0，2026-09-03 仍在提交；已品牌化为 "Grok Mem"）
- 定位"Persistent Context Across Sessions for Every Agent"，覆盖 Claude Code、OpenClaw、**Codex**（`plugin/.codex-plugin`，hooks：SessionStart/UserPromptSubmit/PreToolUse/PostToolUse/Stop）、Cursor（`cursor-hooks/`）、OpenCode、Gemini 等。
- **源码级核对结论（详见附录 A）：** 捕获粒度是 **PostToolUse 级**（每次工具调用异步生成 observation，类型 `decision/bugfix/feature/refactor/discovery/change`，字段含 title/facts/narrative/concepts/files_read/files_modified/content_hash/relevance_count/agent_type）；**注入策略是会话开始时按时间倒序取最近 N=50 条 observation**（`ObservationCompiler.ts:60 ORDER BY created_at_epoch DESC`），UserPromptSubmit 只做 session-init，**不做逐 prompt 的语义召回**；语义检索靠 MCP 三层渐进披露（`search → timeline → get_observations`）由模型主动调用；所谓 hybrid 是 Chroma 结果与 SQLite 元数据过滤的**交集**（`HybridSearchStrategy.intersectWithRanking`），无 RRF/融合。服务端 schema v33 已有 `agent_events`（`source_adapter`/`source_event_id`/`idempotency_key`）与 `memory_sources`（memory→event 映射）——**即事件级 provenance 已在其新存储层落地**。仓库内有 2026-02 的 LoCoMo 内部评测 playbook（hybrid FTS5+Chroma top-10，J-score 对比 Mem0 66.88%），结果未公开在仓库。
- **影响：** 证明"跨宿主共享记忆 + 记忆类型标记 + 事件级溯源"都已是商品能力；SagaContext 的 `memory_kind` 六分类和"记忆有来源"本身不构成差异。它与 OpenViking 系的根本差别是**注入范式**（recency 索引 + 按需 MCP vs 逐 prompt 语义召回），这恰好是 SagaContext 评测协议应该对照的维度。应作为 §8.1 基线之一。

### 2.3 Claude Code 原生 Auto Memory（2026-02）+ Auto Dream（2026-03）
- `MEMORY.md` 四类（偏好/反馈/项目/引用），启动加载前 200 行；Auto Dream 后台四阶段（Orient/Gather/Consolidate/Prune）在 ≥24h 且 ≥5 新会话时合并去重、相对日期转绝对。
- **影响：** 与 Codex 原生记忆并列，是"宿主自带"基线。报告 §4.1 只写了 Codex，缺 Claude Code 对应项。

### 2.4 Cognee 1.0（2026-06-26）
- remember/recall/improve/forget API，单 Postgres 部署，**Claude Code 插件通过 hooks 自动捕获工具调用，会话结束同步到知识图谱**；同时支持 Codex、Cursor、Cline、MCP。
- 注意其自报基准存在配置不对等（自身 tuned、对手 default）。

### 2.5 ByteRover CLI（原 cipher，Elastic License 2.0）
- 面向 coding agent 的"context tree"记忆，MCP 接入十余种 IDE/CLI，LoCoMo 自评。许可证非 OSI，可作对照不宜复用代码。

### 2.6 Supermemory / Zep-Graphiti / Memanto
- Supermemory：MCP-first、被多篇 2026 综述列为 coding agent 首选，但核心为托管闭源。
- Graphiti：双时态知识图谱，28.9k stars，可作为"时间有效性"方向的对照。
- **Memanto**（arXiv 2604.22085，MIT，1.5k stars）：**13 类 typed semantic memory + 冲突解决 + 时间版本化**，LongMemEval 89.8% / LoCoMo 87.1%（自报）。与 §6.4 的 `memory_kind` 和 P2 的 supersede/冲突检测直接重叠。

### 2.7 OpenViking 自身被低估的部分
- `benchmark/locomo/` 多系统对照脚本（见 §1 #14）。
- Web Studio 已能解析 Claude Code / Codex / Trae 会话并展示 recall → prompt injection → MCP 调用 → capture → commit 事件链（README L161-162），即报告 §6.2 `evidence` 模块的可视化部分上游已有雏形。
- Claude Code 插件的离线 pending queue（§1 #9）——报告 §6.2 `capture` 模块对 Claude Code 是重复建设，对 Codex 才是增量。

## 3. 对"主创新点"的挑战

### 3.1 TypedQuery-aware Weighted RRF ≠ 创新
报告 §6.3 的公式 `score(u) = Σ_i w(query_i) / (k + rank_i(u))` 与以下先例完全一致：

| 先例 | 内容 |
|---|---|
| RAG-Fusion（Rackauckas, arXiv 2402.03367, 2024；Raudaschl/rag-fusion 参考实现含 BEIR 评测） | 原查询 + LLM 生成多查询 → 并行检索 → RRF(k=60)；实测 Hybrid+Diverse 配置 nDCG@10 +19% |
| Weighted RRF / Confidence-Weighted RRF（CCNC 2026） | 明确指出 RRF "对所有查询一视同仁"的缺陷并加权 |
| SuperLocalMemory V3 / V3.3（arXiv 2603.14588 / 2604.04514） | **按查询类型（single/multi-hop/temporal/open-domain）给各检索通道调权重乘子**后 WRRF(k=60)，LoCoMo 上做过消融；作者自述 7 通道在 single-hop 上出现融合噪声回归 |
| Scaling RAG with RAG Fusion（arXiv 2603.02153，工业部署） | chunk 级去重每列只算一次、以原查询为锚重排；提醒 recall 提升在生产约束下不一定转化为答案质量 |

**结论：** "把 planner 的 priority 映射成 RRF 权重"是 5 分钟就能被审稿人或面试官指出先例的做法。它值得做，但只能写成"实现了 X"，不能写成"提出了 X"。

### 3.2 真正可能构成差异的三点（建议重排优先级）

1. **记忆证据链（Evidence Ledger / Provenance）** — 上游 issue #3329 明确要求 session_id + message_id + 多消息映射；dreviho 只有 `[Source: uri|type|score]` 级 citations；claude-mem 的服务端 schema 已有 `memory_sources → agent_events` 事件级映射（见 §2.2），但只服务于自己的存储，不覆盖 OpenViking 的 `viking://` 记忆。因此 SagaContext 的 provenance 叙事要精确为：**在 OpenViking 记忆之上补齐"注入的每条记忆 → 原始 turn / tool call / git revision"的闭环，并把 OpenViking 已有的 `record_used` 反馈与检索观测轨迹（`include_provenance`）串成一条可审计的账本**。"业界没人做溯源"这种说法不成立，不要这样写。这也天然对接 LongMemEval-V2 的 "compact evidence" 口径。
2. **可解释的融合分解 + 无回归评测协议** — 输出每个候选的 (query_id, rank, weight, 子分数, 去重/降级原因) 并把它变成可对比的 JSONL trace，再加固定的 NoMemory / FullHistory / 宿主原生 / OpenVikingNative / claude-mem / openviking-hooks / SagaContext 消融矩阵。这是"评测层"的价值，市面上缺乏跨系统可复现协议（多篇综述都指出各家 benchmark 数字不可横比）。
3. **TypedQuery 保真 + 累加融合** — 作为**向上游的 PR**（路线 B）。改动面：`expansion.py` 返回 `List[TypedQuery]`、`gather.py` 的 `dedupe_keep_best`/`_dedupe_candidates` 改为累加、`_semantic.py:410-420` 加跨查询去重。这样既贡献上游，又使 SagaContext 不依赖"上游有 bug"作为存在理由。

### 3.3 `memory_kind` 六分类需要映射而非新建
OpenViking 已有 `events / entities / preferences / experiences` 四个配额桶，以及 `cases / patterns / tools / trajectories / skill-usage` 等不占桶的内置类型（`params.py:16-22`）。报告 §6.4 的 `decision/constraint/failure/workflow/convention/fact` 若另起一套，会与上游桶和配额机制冲突。建议：`memory_kind` 定义为 OpenViking 类型之上的**标签**，并给出到 `MEMORY_CATEGORIES` 的映射表；同时参考 Memanto 13 类看是否有遗漏（如 `environment_gotcha` 对应 LongMemEval-V2 的 "Environment gotchas"）。

## 4. 评测设计的问题

### 4.1 LongMemEval-V2 是 web-agent 基准，不是 coding 基准
README 原文："pairs manually curated questions with long histories of **multimodal web-agent trajectories**"，两个领域是 **web 和 enterprise**。它测的是"在定制环境里成为知识丰富的同事"，和 coding agent 的记忆需求（跨会话的约束/决策/失败模式）在能力分类上有相通之处，但语料完全不同。把它设为主基准会让 SagaContext 的核心结论建立在非目标域上。

### 4.2 建议的基准组合
| 基准 | 用途 | 备注 |
|---|---|---|
| **MemoryCode**（Rakotonirina et al., arXiv 2502.13791, 2025） | **主基准候选**：多会话 coding 交互，测试"未被提示时自发应用早先规则"（prospective memory）与规则更新后取最新 | 模板生成、单域；正是 coding agent 记忆的核心场景 |
| **LongMemCode**（CataDef/LongMemCode，MIT） | 代码记忆**检索**基准：20 corpora / 16 语言 / ~8k 场景 / AST 确定性 GT，无 LLM judge | vendor（ArgosBrain）自建，其引擎为 top；只用其 runner 与数据，不引用其结论 |
| **LoCoMo** | 与 OpenViking 自带 `benchmark/locomo/` 多系统脚本对齐，可直接复用 mem0/supermemory/claudecode 基线 | 对话记忆，非 coding |
| LongMemEval-V1/V2 | 副基准，用于与通用记忆系统横比 | V2 保留其 Accuracy/Latency/LAFS 口径 |
| 自建 Coding 任务集 | 从真实 Codex/Claude Code transcript 回放 | 报告已有，需明确标注规模 `[TARGET]` |

### 4.3 基线矩阵需增补
§8.1 的 6 个基线应加入：**宿主原生**（Codex memories / Claude Code auto memory）、**claude-mem**、**openviking-hooks**。否则无法回答"为什么不用现成的"。

## 5. 路线建议：A → "A+B 混合"

| | 报告方案 | 建议调整 |
|---|---|---|
| 路线 B | "后续实验分支" | **提前到 M0/M1**：向 OpenViking 提 TypedQuery 保真 + 累加融合 PR。改动小、对上游有价值、也是最好的"源码级理解"证明 |
| 路线 A | Gateway 承担 RRF + 去重 + 预算 + 证据 + 评测 | Gateway 收窄为 **Evidence Ledger + Policy 实验层 + Eval Runner**；预算/配额/分层继续用上游（已完整）；RRF 融合以"可插拔策略"存在，用于消融，不作为存在理由 |
| Host Adapter | 双宿主薄适配 | Claude Code 侧直接复用上游 9-hook 插件，仅加 evidence 上报；**Codex 侧补 pending queue** 是真增量（上游 Codex 插件无磁盘队列） |
| 许可证 | 不复制 AGPL 服务端 | 补充：`agent-plugins/` 亦为 AGPL-3.0；若 Host Adapter 借用其 `.mjs` 代码，SagaContext 的适配器部分需按 AGPL 处理或重写 |

**为什么要这样调：** 如果不提前做 B，SagaContext 的"主创新点"随时可能被上游或 openviking-hooks 的下一个版本覆盖；如果提前做 B，则 SagaContext 天然站在"上游已具备 TypedQuery 融合、我在其上做证据链与评测"的位置，叙事更稳。

### A.2 dreviho 关键代码事实
- `scripts/auto-recall.mjs:371-392 rrfMerge` 返回 `{...item, rrfScore}`；随后 `postProcess`（L242-259）与 `getRankingBreakdown`（L129-154）只读 `item.score`，`rrfScore` 无任何消费者。`openclaw-plugin/src/hybrid-search.ts:37-58` 同样在 `.map(e => ({...e.item, score: e.item.score}))` 处丢弃融合分。
- grep 通道伪分数 `score: 1.0/(i+1)`（L363），使 grep 首条在后续按 `score` 排序时压过所有语义命中（语义分通常 <1）。
- 排序常数全部手调（`ranking.mjs:76-86`），无消融；`TEMPORAL_QUERY_RE` 含 `last|next|day` 等高频词，误触发率未测。
- 召回请求 `score_threshold: 0.15, since: "90d"`（记忆）硬编码在 `searchScope`（L319-328）。
- 每条注入含 `[Source: uri | type | score]`，但 uri 指向 OV 记忆节点，不指向原始消息。

### A.3 claude-mem 关键代码事实
- 注入：`src/services/context/ObservationCompiler.ts:60 ORDER BY o.created_at_epoch DESC`，上限 `CLAUDE_MEM_CONTEXT_OBSERVATIONS=50`；UserPromptSubmit → `session-init`（`src/cli/handlers/session-init.ts`），非召回。
- 检索：`SearchOrchestrator` 先 Chroma，空则回退 SQLite FTS；`HybridSearchStrategy.intersectWithRanking`（L111-121）按 Chroma 顺序取与元数据过滤集的交集。
- 类型：`src/types/database.ts:30`。
- Provenance：`src/storage/postgres/schema.ts:169-186 agent_events`、`:240-253 observation_sources`（`source_type ∈ agent_event/session_summary/observation_reindex/manual`）；SQLite `SERVER_OWNED_TABLES` 含 `agent_events`、`memory_items`、`memory_sources`（`src/storage/sqlite/schema.ts:5-16`，schema v33）。
- 评测：`.maestro/playbooks/Wizard-2026-02-22/2026-02-22-LoCoMo-Eval/`，方法为 hybrid top-10 → 12K char → Opus 4.6 作答，J-score/F1 双指标，与 Mem0（66.88%）、full-context（72.90%）对比；未见结果文件。

### A.4 对 SagaContext 的直接结论
1. 三个系统都**没有把 planner 的 TypedQuery 类型带到排序**，也没有真正生效的多路融合——这一空缺仍在，但如 §3.1 所述，它是"实现空缺"而非"方法创新"，最佳归宿是上游 PR。
2. **Provenance 分两层**：事件级（claude-mem 已做，OpenViking 缺，#3329 在要）与"注入→引用"闭环（三者都没有）。SagaContext 应同时补两层，且以后者为主叙事。
3. 评测协议必须覆盖**两种注入范式**（recency 索引 vs 逐 prompt 召回），否则无法回答"为什么不用 claude-mem"。
4. Codex 侧的离线补偿队列在三个系统中都缺，是明确、可验证的工程增量。
