## 2. 按优先级列出的发现

### F01 · P1：把设计假设写成已验证结果，不能据此冻结设计

**报告位置：** 33–38、440–443 行。

H3 写成“成立，Token 成本在 3% 以内”，H4 写成“成立，消除污染和错误强化”，H5 写成“静态规则显著优于在线微调”。但正文没有对应样本、实验配置、调用账单、运行日志或统计结果；`[RUN]` 仅在开头说明中出现。H3 的 3% 与指标中的 3.5% 也未解释口径差别。

这不是必须先完成大规模 benchmark 的要求，而是必须区分“建议先做静态策略”和“已经证明静态策略更好”。同理，列出 12 个测试场景不能算测试通过。

**修订要求：**

- H1：改为“旁路能力存在源码支持，指定配置下的完整链路待验证”。
- H2：改为“提出接口候选，原子性与过滤等能力差异尚未解决”。
- H3/H4/H5：标 `[VERIFY]`；预算与排序参数标 `[TARGET]` 或 `[DESIGN]`。
- 将“冻结 v0.3”改为“形成待验证草案，完成准入探针后再冻结”。
- 用任务书的发现模板补一手来源；当前泛指目录、`v0.1.40+` 这种版本范围不足以复现。

### F02 · P1：OpenViking 原生 CAS 的判断不成立

**报告位置：** 199、300、382–388 行。  
**证据：** E1、E2、E5。

报告将“正文存在 version 字段”推导成“可直接 CAS 覆写”，并要求所有后端实现 `write_atomic(expected_version)`。但所指 OpenViking 固定版本的写入请求没有调用方预期版本参数，路由也没有传入该条件。Mem0 的普通 `update` 同样不能证明具备条件写入。

`读 version → 客户端比较 → 普通 write` 仍有并发窗口；在正文写一个新版本号不会让这组操作自动原子化。能力表把更新、删除和乐观并发合在一格，也掩盖了这一差异。

**修订要求：** 拆成单独能力项。CAS 放在本地权威账本事务里，后端原生条件写入作为可选能力；若采用适配器单写者队列，明确其仅覆盖受该队列管理的写入者。不得声称该公共内容接口已经提供原生 CAS。

**补证探针：** 两个客户端拿同一版本并发修改，证明一方条件提交失败，或证明账本能串行形成正确修订；不能只观察最终 version 数字变大。

### F03 · P1：Codex 工具事件能力表与已有源码直接冲突

**报告位置：** 26、127–135、208–215 行。  
**证据：** E7、E8、E9。

报告断言 Codex“仅 4 个事件，完全缺失 PreToolUse/PostToolUse”，据此规定只能在 Stop 后补偿。核对已有 `728cb12` 快照，事件列表已有工具前后、压缩前后及会话结束事件，工具调度中也有调用路径。

这足以推翻报告对 Codex 源码能力的一概否定，但不足以证明某个已安装发行版、桌面形态、插件配置已经启用所有能力。不能从一个上游记忆插件注册了哪些事件反推整个宿主只支持那些事件。

**修订要求：** 按“宿主形态 + 可执行版本 + 配置/开关 + 源码版本 + 实测事件”重做矩阵；保留能力探测与降级，而非把 Stop-only 固化为架构前提。Claude Code 的 hook 返回格式也需按指定版本补官方契约和探针，不能凭概括性 JSON 示例冻结协议。

### F04 · P1：声明本地账本权威，接口却仍把后端当权威

**报告位置：** 61、117、300–310、365–388 行。

推荐方案说 SQLite 为权威、后端只是检索投影，但 SPI 的 `get_by_id` 定义成“拉取权威实体”，要求后端 CAS 和原子取代；场景中又靠后端版本判断重放完成。

缺少的关键协议是：本地提交成功但索引未更新时怎么办？旧投影迟到并覆盖新投影怎么办？删除与索引写入乱序时如何防止复活？没有这些边界，“即刻过滤”“100% 一致”并不成立。

**建议设计（待批准）：**

1. `MemoryLedger` 负责权威内容、修订、证据、删除状态与条件提交。
2. 同一本地事务提交修订和 outbox 事件，避免“账本已提交但没有同步任务”。
3. `SearchBackend` 只负责投影写入、删除和搜索；明确单写者/序列化或版本栅栏方案，以及幂等键、失败恢复和重建协议。
4. 搜索命中仅为候选，按稳定 ID 回查账本，复核当前版本、状态、作用域与权限后才注入；索引滞后可能降低召回率，但不能让旧事实重新生效。
5. Mem0 的内部 UUID 与 SagaContext 稳定 ID 分别管理。报告中的 `write_raw(id=UUID, ...)` 若是待实现适配器方法，应显式标注，不能当作已核对的公开 API。

**后端旁路补充：** E4 支持 Mem0 普通向量记忆提取分支的旁路，但 E3 表明 OpenViking 写内容仍默认刷新语义与向量。“绕过 Session 记忆抽取”不等于“完全没有模型/语义处理”。应单独核对 processing mode、正文保持、索引可见性与成本。

### F05 · P1：项目身份与任务接续仍会合并不该共享的上下文

**报告位置：** 71–90 行。

- root commit 相同的 fork 可具有不同项目身份与约定；对同一个 root commit 做同样哈希必然得到相同 key，不能阻断这种污染。
- Git 可存在多个根提交、浅克隆和重写历史；报告假定“唯一初始 commit 恒定”，没有处理这些边界。
- monorepo 的相对路径若直接取当前 cwd，会把普通子目录误当项目；如果取子项目根，需要给出根发现规则。
- 非 Git 路径哈希在移动目录后改变；仅称“持久化映射”没有定义重定位关联。
- 任务规则虽先说不能只看分支，条件 1 仍直接按同分支接续；且新会话开始时可能还不知道新目标。条件 2 自动暂停旧任务又可能影响另一活跃会话。

**修订要求：** 使用显式项目记录与可配置的身份关联；Git ancestry、remote、路径和 worktree 关系作为识别信号，而非单一权限身份。fork 是否共享须有明确策略。任务接续结合显式任务 ID/用户确认、目标与触及对象；歧义时不强制合并，不暂停其他活跃会话。

**最小补测：** fork 与上游隔离、两个 worktree 按策略共享、同分支不同目标不合并、非 Git 项目移动、monorepo 普通目录切换不换项目。

### F06 · P1：exit code 为 0 被当成了足够的事实验证

**报告位置：** 96–98、120–121、227–246 行。

“某条命令返回 0”只说明该命令成功结束，不能单独证明它检验了所声称的故障、根因或修复。构建通过也不能单独证明探针运行正常。场景 A 的用户陈述与命令成功之间缺少针对性验证，不能直接据此写成项目事实。

同时，“任何经验都必须 exit code 0”过窄：用户画像、明确偏好、已复现但尚无修复的风险提醒不适用同一个验证器。未修复故障可保留为低确定性、带条件的警告，不应伪装成已验证修复，也不必一概丢弃。

**修订要求：** 建立 `claim → evidence → verifier → result → environment/version` 的对应关系；对不同记忆类型使用不同晋升条件。示例写为合成场景并移除未经核对的产品事实。重复事件去重与“独立证据”判定分开，不能仅靠不同 tool_call_id 就认定为独立确认。

### F07 · P1：遗忘、安全与上下文权限还只停留在声明

**报告位置：** 25、109、318–349、392、415–416 行。

报告一方面“不物理硬删”、一方面提供 `hard_delete` 和 tombstone 验收，但模型没有删除语义和再导入抑制策略。把记录设为 `retired` 不等于清除账本、证据、投影、缓存和旧 transcript 派生结果；tombstone 也不能无期限保留被要求删除的完整敏感正文。

模型同时缺少显式 user/owner、task_id、有效期/适用版本及结构化来源信任信息。单用户 MVP 可以固定 owner，但必须写明部署边界；task 记忆至少要能够在同仓库内区分任务。`verified_success: bool` 不能替代验证对象与验证器。

T11 只做文本转义不足以证明不会执行不可信指令。HTML/XML 标签转义只是格式处理，不能被当成工具权限隔离。

**修订要求：** 区分业务退役、修订留档和用户删除；定义删除范围、投影确认、再导入抑制与最小非敏感删除标记。命令型规则的启用需要权限与审批设计，不能由召回正文自动升级。

### F08 · P2：评测矩阵齐全，但不能据此判断“最佳策略”

**报告位置：** 169–187、401–417、429–430 行。

- 正文列出基准名称，却没有在本报告中补数据版本、下载/复现入口、划分和许可证；历史文档的检索入口不等于本轮已核对实验适用性。
- SA 用“输出包含新事实且严格排除旧事实”会误伤“旧方案 A 已废弃，现采用 B”这样的正确回答，也可能奖励表面关键词命中。
- CRP 把注入与最终输出混成概念；分母是记录数还是事件数不清楚，且系统完全不注入也可能获得表面零污染。
- PGR 强制 git_commit 不适用于全局偏好或非 Git 项目；应按证据类型定义可定位条件。
- 总 token 成本没有清楚区分提取、嵌入、查询扩展、注入输入与任务输出；固定延迟、90 天、0.45、500 次纠正等数字都缺少实测依据。
- “12 个确定性用例全通过”可以作功能准入，但不是学习收益或统计显著性的证据。

**修订要求：** 分开评测召回、注入、事实正确性、演化与任务质量；允许正确的历史对照表述。误注入率必须与必要记忆召回率一起报告。明确比较宿主、模型、数据切分、预算与原生记忆开关。单独消融账本、作用域、锚定、预算和个性化参数，不能把整个 SagaContext 的收益都归因于个性化。

### F09 · P2：竞品差异化与许可证结论写得过满

**报告位置：** 18、48、52、203、437 行。

“通过 HTTP 隔离许可证传染”“现有系统在锚定增量和作用域安全上系统性缺失”等都是超过本报告证据的概括。许可证应按组件、版本与集成方式记录，不能把进程边界当成法律保证。本轮未作法律合规结论。

架构选择可以基于维护成本与职责清晰度，而不必先证明竞品完全没有类似功能。Mem0 原生对已有记忆的输入处理等机制也应纳入对照，区分“有类似机制”“满足我们的语义契约”“在目标任务上有效”三个层次。

**修订要求：** 为每项差异化绑定具体源码/实验与版本；否定结论写明搜索范围。没有足够证据时保留“未确认”，不将其升级成产品定位依据。

## 5. 不必重做全面调研，只补六个准入探针

| 探针 | 输入/操作 | 最小交付与通过条件 |

**建议的下一步不是立即冻结 v0.3，而是先纠正事实和接口边界，完成上述有限补证。真实统计收益可留到后续；但基本能力不能在未验证时当作已存在。**
