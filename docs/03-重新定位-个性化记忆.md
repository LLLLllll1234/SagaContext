## 1. OpenViking 的个性化机制现状（源码核对 `a838014`）

### 1.1 已有的东西

| 机制 | 位置 | 现状 |
|---|---|---|
| **用户记忆类型** | `prompts/templates/memory/*.yaml`；`docs/en/concepts/02-context-types.md:59-67` | profile（单文件）、preferences（按 topic 分文件）、entities、events；另有 identity/soul（**Agent 人格**，非用户）、cases/trajectories/experiences（**Agent 经验**，`agent_only: true`） |
| **字段级合并语义** | `session/memory/merge_op/{patch,replace,sum,immutable}.py`；registry 默认 `patch` | preferences.content 用 SEARCH/REPLACE patch；profile 靠 prompt 指令"keep latest if conflicting"。**没有** validity / supersedes / 置信度 / 证据计数 |
| **命名空间分层** | `core/namespace.py`：`viking://user/{uid}/memories`、`peers/{peer_id}`、`viking://agent/...`；`gather.py:119-127` origin = self / actor_peer / other_peer | 用户 vs 多 Agent（peer）已分层；other_peer 有分类惩罚 |
| **使用反馈回路** | `POST /sessions/{id}/used`（`sessions.py:835`）→ `session.py:2770 increment_active_count` → `memory_lifecycle.hotness_score` → `hierarchical_retriever.py:607-624` `(1-α)·semantic + α·hotness` | 已闭环，但 α 是**全局配置** `retrieval.hotness_alpha`，与用户、类型、项目无关；只有正反馈，无"被注入但没用/被否定"的负反馈 |
| **Profile 注入** | Claude Code / Codex 插件 SessionStart 注入 profile.md + preferences/entities 索引（≤10000 token） | 存在；`gather.py:235` 在逐 prompt 召回中**排除** profile.md，避免重复 |
| **时间衰减 / 保留** | `memory_lifecycle.py` 半衰期衰减；`session/retention.py` 会话消息预算 | 有衰减，无按用户/类型差异化的遗忘策略 |

### 1.2 关键缺口：schema 是"消费级助手"口径，不是"开发者"口径

- `profile.yaml` 的示例字段：出生日期、性别、年龄、籍贯、居住地、**恋爱状态**、职业规划——这是 VikingBot（消费级）的人设模板。
- `preferences.yaml` 的 topic 示例："Python code style, Communication style, **Food preference, Commute preference**"。代码风格只是众多 topic 之一，没有结构（语言 / 框架 / 测试 / 错误处理 / 命名 / 评审口味 / 风险偏好），也没有**项目级 vs 全局级**区分——preferences 目录固定在 `viking://user/{uid}/memories/preferences`，不能表达"在 repo A 用 tabs、在 repo B 用 spaces"。
- 用户纠正（"别用 any"、"测试放 tests/ 不放 src/"）没有独立类型；它们要么被抽成一条 preference bullet，要么被丢弃。抽取 prompt 明确要求"omit ... supporting evidence"，即**纠正发生时的原始上下文被抽掉**。
- Agent 侧的 experiences/trajectories 是"Agent 学到什么对任务有效"，不是"这个用户希望 Agent 怎么做"。两者在 OpenViking 里都叫 memory，但个性化只关乎前者的**用户面**。

**一句话：** OpenViking 提供了个性化所需的全部**机制**（类型化 schema、字段合并、命名空间、使用反馈、分层注入），但其**内容模型**是通用助手的，对 coding agent 用户而言几乎空白；而且反馈只调一个全局 α，谈不上"越用越懂你"。

## 2. "更个性化"对 coding agent 意味着什么（建议定义）

把"个性化"拆成四层，每层都能对照 OpenViking 现状说清增量：

| 层 | 问题 | OpenViking 现状 | 增量 |
|---|---|---|---|
| **P1 开发者画像 schema** | 记什么 | 消费级 profile/preferences | 开发者口径的类型：`convention`（可执行的规则）、`correction`（带原始上下文的纠正）、`tool_habit`、`review_taste`、`risk_tolerance`、`explanation_style`；每条带 **scope = global / repo / path-glob** |
| **P2 偏好演化** | 变了怎么办 | patch + "keep latest" | 每条偏好带 `valid_from / superseded_by / confidence / evidence_count / last_confirmed`；非单调变化（加强/减弱/反转）显式建模；冲突时进入待确认队列而不是静默覆盖 |
| **P3 反馈驱动的召回个性化** | 怎么越用越准 | 全局 α 的 hotness | 按用户×类型×scope 学习注入权重；负反馈（注入但未引用、被用户否定）计入；把 `record_used` 与最终回答引用对齐成训练信号 |
| **P4 从"记住"到"遵守"** | 记住了还犯 | 只注入文本 | 把 `convention/correction` 编译成可检查的规则（lint 命令、路径约束、PreToolUse 拦截），注入时附带"上次违反于 X"——参考 TRACE 论文的结论：Mem0 记住了偏好仍有 57.5% 的适用检查被违反，**问题不是遗忘而是不强制** |

P1+P2 是"个性化记忆系统"的本体；P3 是"越用越个性化"；P4 是 coding 场景独有、且当前学术界刚刚证明必要的那一层。

## 3. 竞品与先例（针对"个性化"重新扫一遍）

| 项目 / 论文 | 与本项目的关系 | 可借鉴 / 需回避 |
|---|---|---|
| **Mem0**（user/agent/run 作用域、user profile、`preference` 类型建议） | 通用个性化记忆的事实标准 | 借鉴其"typed schema + 保守写入（只存用户确认或已合并代码印证的记忆）"建议；回避把自己描述成"另一个 Mem0" |
| **Memobase / MemMachine / PGMem** | profile 型记忆专门户；PGMem 用 typed edge 把 persona 信号绑到 grounding event，带 validity 衰减 | **PGMem 的 validity + grounding 正是 P2 要做的**；需说明我们在 coding 域、且以 viking:// 文件系统承载 |
| **PERMA / PersonaMem / PrefEval / Memora / MemoryCD** | 个性化记忆基准，全部是**生活助手**人设（电影、旅行、饮食）| 方法论可借（事件驱动偏好演化、非单调变化、Turn≤2 恢复率），语料不可用；**开发者偏好基准是空白**——机会 |
| **TRACE / tellonce**（arXiv 2606.13174，MIT） | "把用户纠正编译成运行时强制"，Claude Code skill 已开源 | **P4 的直接先例**。我们的差异：纠正来自 OpenViking 持久记忆而非单会话；跨 Codex/Claude Code；带 scope 与演化 |
| **PROJECTMEM**（arXiv 2606.12329，MIT） | 本地事件日志 + pre-action gate（"这个修法上次失败过"），Claude Code/Cursor/Codex MCP | "Memory-as-Governance"框架可引用；它是**项目记忆**不是用户偏好，正好互补 |
| **Claude Code Auto Memory / Auto Dream** | 宿主原生：MEMORY.md 四类（含 user preferences），Dream 做合并去重 | 是基线；它无 scope、无演化模型、无强制 |
| **VS Code Copilot agent memory** | 跨 workspace 的偏好/约定记忆文件，agent 自选 scope | 证明"scope 自选"是产品共识；我们要做的是可评测的版本 |
| **claude-mem / dreviho** | 见审核意见附录 A | 都没有用户偏好模型；claude-mem 的 observation 类型是"发生了什么"，非"用户想怎样" |

结论：**"开发者个性化记忆 + 偏好演化 + 遵守强制 + 可评测"这四件事没有一个开源项目同时做**，且个性化基准全在生活助手域。这是比"Weighted RRF"扎实得多的差异化。

## 4. "利用 OpenViking 的方法"的两种解读（需要用户拍板）

| | **解读 A：OpenViking 作引擎（sidecar）** | **解读 B：借其方法，独立实现** |
|---|---|---|
| 做法 | OpenViking 跑存储/Session/抽取；本项目提供开发者 schema（自定义 memory type yaml 是上游支持的扩展点）、演化层、反馈学习、强制层、评测 | 用 viking:// 式虚拟文件系统 + L0/L1/L2 + 类型化 schema/merge_op + Session commit 抽取这套**方法**，自己实现一个面向个人开发者的轻量系统（如 SQLite + Markdown + 本地 embedding） |
| 增量清晰度 | 高：所有新东西都在 OpenViking 之外，边界干净 | 中：要向别人解释"哪些是 OpenViking 的思想、哪些是你的" |
| 工程量 | 低-中：schema yaml + 演化/反馈/强制/评测四个模块 | 高：先重造基础设施再做个性化 |
| 许可证 | AGPL 服务端独立进程，HTTP/MCP 调用；自定义 schema 属配置 | 无 AGPL 牵连（不复制代码） |
| 风险 | 依赖上游 API 稳定性；个性化受限于上游抽取管线能力（可通过自定义 type + 自己的抽取 prompt 缓解） | 容易演变成"又一个记忆库"，个性化被基建吞掉 |
| 适用 | 目标是**尽快验证"个性化能否让 coding agent 更好用"** | 目标是**拥有完整系统 / 简历叙事需要"从零实现"** |

**建议：解读 A。** 理由：个性化的价值只有靠评测证明，A 让所有精力花在 P1-P4 与评测上；而且 OpenViking 的 memory type 本来就是 yaml 可扩展（`memory_type_registry.py` 读 `fields[].merge_op`），开发者 schema 可以作为它的一组自定义类型直接落地，不必碰服务端代码。

## 5. 若走解读 A，重新框定的项目骨架

```
Codex / Claude Code hooks (复用上游插件事件)
        │  transcript / tool 轨迹 / 用户纠正信号
        ▼
[Correction Miner]  ──► 识别纠正、约定、口味；保留原始 turn 作 grounding
        │
        ▼
[Developer Memory Schema]  自定义 OpenViking memory types (yaml)
   convention / correction / tool_habit / review_taste / risk_tolerance
   每条: scope(global|repo|glob) · valid_from · superseded_by · confidence · evidence[]
        │  写入 viking://user/{uid}/memories/dev/...
        ▼
[Preference Evolution]  冲突检测 → 待确认队列 → supersede；非单调变化建模
        │
        ▼
[Personalized Recall Policy]  按 用户×类型×scope 的注入权重；
   正反馈 = record_used + 回答引用；负反馈 = 注入未用 / 被否定
        │
        ▼
[Compliance Layer]  convention → 可检查规则 (PreToolUse / lint / 路径约束)
        │
        ▼
[Eval]  开发者偏好基准（见 §6）+ 与 Claude Code Auto Memory / Mem0 / tellonce 对照
```

分期：M1 = P1 schema + Correction Miner + P2 演化 + 基准 v0；M2 = P4 强制层；M3 = P3 反馈学习召回（见 §8）。

## 6. 评测：开发者偏好基准（当前空白，是本项目最可能被认可的产出）

- **Ground truth 来源**：用户自己的 Codex / Claude Code transcript 中的**纠正事件**（"不要 X"、"改成 Y"、撤销 Agent 修改后手动改回）。每条纠正天然给出：偏好内容、scope（发生在哪个 repo/路径）、时间。
- **任务构造**：仿 MemoryCode（arXiv 2502.13791）的"未被提示时自发遵守"——在后续任务中不提及偏好，检查产出是否遵守；仿 PERMA 的事件驱动演化——同一偏好在 T1 建立、T2 反转，检查 T3 是否用最新版。
- **指标**：偏好遵守率（TRACE 口径的 violation rate）、演化正确率（反转后用新版的比例）、Turn≤2 恢复率（PERMA 口径）、误注入率（把 repo A 的约定带到 repo B）、注入 token、用户重复纠正次数（真实使用日志）。
- **基线**：NoMemory / Claude Code Auto Memory / OpenViking 原生 preferences / Mem0 / tellonce(单会话强制) / 本项目。
- 所有数字标 `[TARGET]`，与原报告纪律一致。

## 8. 已拍板（2026-09-04）

1. **解读 A：OpenViking 作引擎。** 本项目不复制服务端，以自定义 memory type yaml + 独立的演化/反馈/强制/评测模块叠在其 HTTP/MCP 边界上。
2. **四层全做（P1–P4），但按依赖分期：**
   - **M1 本体**：P1 开发者 schema + Correction Miner + P2 演化模型 + 基准 v0（§6）。没有 P1 的结构化偏好，P3/P4 没有输入。
   - **M2 遵守**：P4 Compliance Layer——把 M1 的 convention/correction 编译成 PreToolUse 拦截 / lint / 路径约束；用 TRACE 口径的 violation rate 对照"只注入文本"的 M1。
   - **M3 越用越准**：P3 反馈学习召回——用 M1/M2 积累的 record_used + 引用 + 违反/否定信号训练用户×类型×scope 注入权重；这是最像研究课题的一层，放最后是因为它需要前两期产生的真实使用数据。
   - 每期都以 §6 基准的同一套指标出报告，形成"文本注入 → 强制 → 学习召回"的消融链，而不是三个孤立功能。
