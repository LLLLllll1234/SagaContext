## 0. 一句话

SagaContext 是叠在 OpenViking 之上的**分层开发者个性化记忆**：会话开始时按层召回与当前项目/任务相关的已有记忆，会话结束时**以这些已有记忆为锚**对账更新，而不是每次从零抽取。记的不只是"你希望怎么做"（偏好层），也包括"这个项目是什么"（项目层）、"你正在做什么"（任务层）。

## 1. 这轮改了什么

| 03/04 的说法 | 本文档修订为 | 原因 |
|---|---|---|
| 项目记忆是 PROJECTMEM 的事，"互补、不做"（03 §3） | **项目层是一等层**，与偏好层并列 | 用户需求的核心是"随会话进行维护完善项目记忆"；repo scope 的 convention 只能表达"在这个 repo 你希望怎么做"，表达不了"这个 repo 是什么" |
| 只有用户面的四个类型（profile / taste / convention / correction） | 六层：用户 / 偏好 / **项目 / 任务 / 团队-peer / Agent 经验** | 后三层多数可映射到 OpenViking 已有机制，增量是统一的对账循环与来源标注 |
| Correction Miner + Evolution Reconciler 只服务偏好 | 泛化为**通用对账循环**，每层套用 | 避免每层各写一套抽取与冲突逻辑 |
| DevPref-Bench 只评偏好 | 扩到项目记忆与任务接续 | 项目层没有评测就没有存在证明 |

**没改的：** OpenViking 作引擎、不改服务端；写回仍以会话末为主（Stop / SessionEnd / PreCompact），会话中只召回不写回；grounding、冲突进确认队列、数字全部 `[TARGET]` 四条边界不变。

## 2. 六层模型

| 层 | 记什么 | scope | OpenViking 现有承载 | SagaContext 增量 | 期 |
|---|---|---|---|---|---|
| **L1 用户层** | 我是谁：技术栈、经验、角色、解释语言、口味 | global | 内置 `profile`（消费级字段） | `dev_profile` / `dev_taste`（04 §2.3） | M1 |
| **L2 偏好层** | 我希望怎么做：可判定的约定、纠正事件 | global / repo / glob | `preferences`（按 topic 分文件，无 scope） | `dev_convention` / `dev_correction` + 演化 + 遵守（04 §2–5） | M1 / M2 |
| **L3 项目层** | 这个项目是什么：架构决策、模块地图、环境坑、约束 | repo / glob | **无对应用户类型**（`viking://resources` 是原始资料不是记忆；`events/entities` 是通用助手口径） | 新类型 `dev_decision` / `dev_project_map` / `dev_gotcha`（§3） | M1 |
| **L4 任务层** | 我正在做什么：目标、已完成、未决、下一步、所在分支 | repo × task | 无（session 只是原始消息流） | 新类型 `dev_task`；新会话开始接续，结束后归档并把可沉淀事实提炼进 L3（§4） | M1 |
| **L5 团队/peer 层** | 同一 repo 里别人定的约定与决策，与个人记忆区分来源 | repo | peer 命名空间 `viking://user/{uid}/peers/{peer_id}/...` 是"当前用户边界内的交互对象"，其他用户不可见，**不适用**；可用的是共享 scope `viking://resources/...` + group ACL | 载体定为 `viking://resources/sagacontext/team/{repo_key}/`（§9 决议 1）；来源标注 `origin=team` + 与 L2/L3 冲突时的优先级规则 | M4 |
| **L6 Agent 经验层** | 对这个用户/项目哪种做法有效 | user × repo | `experiences / cases / trajectories`（`agent_only`，已有 supersedes） | 不新建类型；只做召回策略与 P3 反馈学习的信号来源 | M3 |

**层之间的关系：**
- L1/L2 跨项目跟人走；L3/L4 跟 repo 走；L5 跟 repo 走但来源不是本人；L6 跟 (人, repo) 走但视角是 Agent。
- 召回时的注入顺序：L4（如果有活跃任务）→ L2 生效约定 → L3 相关事实 → L1 → L5/L6。预算见 §6。
- 冲突优先级：L2 个人约定 > L5 团队约定（个人可覆盖团队，但注入时标注"团队约定是 X，你的覆盖是 Y"）；L3 事实与 L5 事实冲突进确认队列。

## 3. 项目层类型（L3）

三个类型，全部 `stage: user`、`directory: viking://user/{{ user_space }}/memories/dev/project/{{ scope_key }}`，复用 04 §2.3 的演化字段（`confidence / evidence_count / contra_count / valid_from / superseded_by / status / last_confirmed / evidence`）与 §2.4 的 grounding 格式。字段级表放 04 v0.2，这里只定语义与合并模式。

| 类型 | 模式 | 唯一键 | 核心字段 | 一句话 |
|---|---|---|---|---|
| `dev_decision` | upsert | `topic` | `decision`（patch）· `rationale`（patch）· `alternatives`（patch）· `affects`（patch，路径/模块列表） | ADR 口径："选了 X 而不是 Y，因为 Z，影响 W" |
| `dev_project_map` | upsert | `component` | `responsibility`（patch）· `paths`（patch）· `entrypoints`（patch）· `depends_on`（patch） | 模块地图，一个 component 一个文件，patch 增量修 |
| `dev_gotcha` | upsert | `topic` | `symptom`（patch）· `cause`（patch）· `fix`（patch）· `trigger_paths`（patch） | 环境坑与失败模式（对应 LongMemEval-V2 的 "Environment gotchas"、PROJECTMEM 的 pre-action gate） |

**什么是"个性化"的项目记忆：** 它是**你**在这个项目里的知识视图——你做过的决策、你踩过的坑、你理解的模块边界——不是全量事件流；每条都有 grounding、有取代关系、冲突进确认队列；跨 Codex 与 Claude Code；可评测。这三点分别对应 claude-mem（append-only observation 流）、Claude Code 原生 MEMORY.md（Agent 自由写、无对账、无 scope）、PROJECTMEM（事件日志 + gate，不区分谁、不跨宿主）各自没有的东西。

**与 L2 的边界：** "测试放 `tests/`" 是 L2 约定（对 Agent 的行为要求）；"`tests/` 用 pytest fixtures 在 `conftest.py` 里集中" 是 L3 project_map（对项目的事实描述）。判定规则：能改写成"Agent 应/不应 X"的进 L2，只能改写成"项目是 X"的进 L3。Reconciler 的 L2 判定输出加一个字段 `layer ∈ {preference, project, task}`。

## 4. 任务层类型（L4）

`dev_task`，upsert，唯一键 `task_id`，目录 `.../dev/task/{{ scope_key }}`：

| 字段 | merge_op | 说明 |
|---|---|---|
| `goal` | replace | 一句话目标 |
| `branch` | replace | git 分支（若有） |
| `done` | patch | Markdown 列表 |
| `open` | patch | 未决项 / 阻塞 |
| `next` | replace | 下一步一句话 |
| `touched_paths` | patch | 涉及文件 |
| `task_status` | replace | `active / paused / done / abandoned`（与公共演化字段 `status` 区分） |
| `started_at` / `last_active` | replace | ISO |

**生命周期：**
- **新会话开始**：同 repo 下若有 `task_status=active` 且 `last_active` 在 14 天内的任务：当前分支与其 `branch` 相同则直接接续；否则注入一行提示，用户说"继续"或新 prompt 与 `goal` 相似度 ≥0.5 视为接续，否则创建新任务并把旧任务标 `paused`（细则见 04 v0.2 §3.7）。
- **会话末**：Reconciler 更新 `done / open / next / touched_paths`。
- **任务完成**（用户说完成、或分支已合并、或 30 天无活动）：`task_status=done`；Reconciler 扫一遍 `done` 与 `open`，把可沉淀的决策/坑/模块知识**提炼进 L3**，任务本体归档不再注入。
- **不做的事**：不追踪细粒度 todo，不替代宿主自己的任务列表；只保证"下次打开这个 repo 知道上次做到哪"。

## 5. 通用对账循环

把 04 §3 的 Correction Miner + Evolution Reconciler 泛化。每层共用同一循环，差别只在候选检测规则和类型判定。

```
SessionStart / UserPromptSubmit（会话中，只读）
   │  按 scope 召回各层 active 记忆 → 锚点集 A
   │  轻量候选检测（L0 规则 / L1 结构）→ 本地候选缓冲 C（不写 OpenViking）
   ▼
Stop（达阈值）/ SessionEnd / PreCompact（会话末，写回）
   │
   ├─ 1. 锚定抽取：把 A 与本会话 transcript 一并交给判定模型，
   │       要求输出的是"相对 A 的增量"：confirm / refine / supersede / new / conflict
   │       而不是从零抽取一遍
   ├─ 2. 分层路由：每条增量标 layer（preference / project / task）与 scope
   ├─ 3. 演化状态机（04 §3.3）：confirm → evidence_count+1；refine → patch；
   │       supersede → 旧 superseded_by；conflict → pending_confirm 进确认队列
   ├─ 4. 写入 OpenViking（自定义类型），evidence 带 grounding
   └─ 5. 写 trace（04 §7.4），含每条增量的锚点 URI 与判定类型
```

**"锚定抽取"是相对 OpenViking 的关键差别。** OpenViking 的 Phase 2 抽取是"从新消息里提取记忆，再按 merge_op 合并进同名文件"；同名靠 `filename_template` 的字段碰撞，语义相近但 topic 不同的记忆会各写一份。SagaContext 把已召回的相关记忆显式作为输入，让模型判断"这和已有的哪一条是同一件事、是补充还是推翻"。claude-mem 的 PostToolUse observation 与 dreviho 的 capture 也都没有这一步（dreviho 只有 >0.85 相似度追加）。

**时机决定（已拍板）：** 会话中只召回、只缓冲候选，不写 OpenViking；写回集中在 Stop（复用上游 20000 token / 10 轮阈值）、SessionEnd、PreCompact。理由：每轮 LLM 对账的延迟和成本不值当，且 OpenViking 的 commit 本来就是这个节奏；"随会话进行不断维护"体现在**每次 commit 都以已有记忆为锚**、以及会话中不断召回更新后的记忆，而不是每轮写盘。

**安全阀：** 对账候选 ≥N（默认 20）条未写回时，即使未达阈值也触发一次写回，防止长会话丢失；Codex 无磁盘队列，本地缓冲 C 落盘 `~/.sagacontext/buffer/<session>.jsonl`。

## 6. 召回与注入预算（M1 基线，替代 04 §4.1）

| 时机 | 注入内容 | 预算 |
|---|---|---|
| SessionStart | L4 活跃任务摘要（若有）→ L2 生效约定（active, conf≥0.5，≤12 条）→ L1 profile + 每 dimension 一条 taste → L3 与 cwd 相关的 gotcha（trigger_paths 命中）| ≤2000 token |
| UserPromptSubmit | L3 语义召回 top-3（decision / project_map / gotcha）+ L2 `dev_correction` top-3（相似度 ≥0.6）| ≤600 token |
| PreToolUse（Edit/Write，Claude Code 有） | 目标路径命中的 `dev_gotcha.trigger_paths` → 一行提示；M2 起叠加 Compliance 检查 | ≤150 token |

排除规则同 04 §4.1：`pending_confirm` / `superseded` 不注入；跨 repo 的 `repo-*` 不注入。L5/L6 在 M1 不注入。

## 7. 评测扩展（在 04 §6 之上）

**新增数据：**
- **项目事实回放**：从用户真实 transcript 里人工标注"项目事实被建立 / 被更新 / 被使用"三类事件，`[TARGET]` ≥40 条、≥3 个 repo。
- **合成演化**：为每条项目事实生成 T1 建立 / T2 事实变化（如目录迁移、依赖替换）/ T3 隐式依赖 的三段会话。
- **任务接续**：截断真实会话于任务中途，新会话不给上下文，看 Agent 是否知道做到哪。

**新增指标：**

| 指标 | 定义 | 层 |
|---|---|---|
| 事实回忆正确率 | T3 任务中 Agent 使用的项目事实与 GT 一致的比例 | L3 |
| 过时事实更新率 | T2 变化后，T3 用新事实而非旧事实的比例 | L3 对账 |
| 锚定命中率 | Reconciler 判为 confirm/refine/supersede 的增量中，锚点确为同一事实的比例（人工抽检） | 对账循环 |
| 重复记忆率 | 语义相同但被写成两条的比例（对照 OpenViking 原生抽取） | 对账循环 |
| 任务接续正确率 | 新会话首轮 Agent 对"做到哪 / 下一步"的描述与 GT 一致 | L4 |
| 误注入率 | repo B 任务中注入 repo A 的项目事实 | L3 scope |

**基线增补：** claude-mem（recency 注入范式）、Claude Code 原生 MEMORY.md、PROJECTMEM、OpenViking 原生 events/entities。偏好层基线沿用 04 §6.3。
