# SagaContext 调研与路线报告

**日期：** 2026-09-03  
**阶段：** 立项调研与路线选择，尚未进入实现  
**暂定项目名：** SagaContext  
**推荐路线：** 独立本地 Policy Gateway + OpenViking sidecar + Codex/Claude Code 适配器

## 1. 执行结论

本项目的首版目标已经确定为：

- 面向单机个人开发者；
- 默认本地运行，会话、代码片段和记忆不离开本机；
- OpenViking 作为必需的本地 sidecar，通过 HTTP/MCP 调用；
- Codex 与 Claude Code 各自接入轻量 Hook/插件，但共享同一个项目级记忆空间；
- 提供 CLI、双宿主适配器和标准化评测接口；
- 暂不做 Web 管理台、团队同步、多租户和云端托管。

原始想法“基于 OpenViking 的 Coding Agent 长程上下文与记忆系统”需要收窄并升级。OpenViking 当前已经包含 Codex、Claude Code 等宿主的记忆插件，具备 Session 生命周期 Hook、自动捕获、自动召回、MCP、分层上下文和 Token 预算。如果只做通用的长程记忆或简单的向量存储，不仅与 OpenViking 上游功能重叠，更无法解决个人开发者的核心痛点。

针对**“基于 OpenViking 的个人 Agent 助手（侧重强个性化 Persona 与个人工作流，而非泛化通用记忆）”**的技术定位，建议将项目明确命名与定位为：

> **SagaContext：基于 OpenViking 的、面向个人开发者的个性化认知编排与私有工作流 Agent 引擎。**

核心增量放在以下五个“个性化与认知对齐”关键维度：

1. **双层记忆隔离与个性化流转（Global Persona vs. Project Ephemeral）：** 利用 OpenViking 的 `viking://user/` 与 `viking://project/` 命名空间，实现个人编程习惯（代码风格、快捷命令、常用库偏好、沟通语气、架构厌恶点）跨项目沉淀，而项目临时决策与 Bug 修复严格限制在本地项目内；
2. **个性化隐式偏好演进（Implicit Preference Mining）：** 从开发者在 Codex/Claude Code 中的高频修改、代码拒绝（Reject/Rollback）、手动修改 diff 中反向挖掘强个性化偏好，实现个人“越用越顺手、免重复提示”的陪伴式个性化；
3. **保留 Query Planner 优先级与个性化意图：** 保留 Query Planner 产生的 `context_type`、`priority`、`intent`，并在 TypedQuery 融合阶段赋予个人习惯（User Persona/Conventions）第一优先级的抢占式配额；
4. **代码符号与时序失效防负迁移：** 结合 Git Commit DAG 与 AST 符号锚定，防止个人历史偏好与特定代码库当前重构状态产生冲突；
5. **白盒可控与人机纠偏回路（Human-in-the-loop）：** 提供本地 Markdown 镜像导出与 CLI 快速纠偏，让开发者对个性化记忆随时“可见、可改、可弃（Revoke/Pin）”。

## 3. OpenViking 调研结论

### 3.1 它已经解决了什么

OpenViking 更准确的定位是 **agent-native context database / context infrastructure**，而不是普通向量库或 RAG 包装层。其核心设计包括：

- 用 `viking://` 统一组织 Memory、Resource、Skill；
- 用 L0 abstract、L1 overview、L2 原始内容实现渐进式加载；
- 将内容存储与向量/索引存储分离；
- 资源摄取经过解析、TreeBuilder、SemanticQueue 和异步语义处理；
- Session 提供归档、上下文和长期记忆提交链路；
- `search()` 支持 Session 上下文、意图分析、层级检索和 Rerank；
- Context Assembler 已提供分类配额、URI 去重、跨轮冷却、分层读取、Token 预算和可选摘要重写。

当前仓库的 `agent-plugins/` 已是 Agent Plugins 1.0 包，提供 MCP stdio proxy 和 `openviking-memory` Skill；README 同时明确列出专门的 `claude-code-memory-plugin` 和 `codex-memory-plugin`。这意味着本项目不能把“同时支持 Codex 与 Claude Code”本身作为主要创新点。

### 3.2 OpenViking 的个性化（Personalization）支持现状与缺口

OpenViking 原生提出了基于统一资源定位的 `viking://` 规范：
- `viking://user/...`：预留的用户作用域（User-level context）；
- `viking://agent/...`：预留的 Agent 自身状态/技能空间；
- `viking://resource/...` / `viking://session/...`：项目资源与会话流水。

**深入源码与现状分析发现的个性化缺口：**
1. **用户空间目前徒有其表：** 在 `agent-plugins` 1.0 实现中，OpenViking 主要按单会话（Session）和当前工作目录（Directory/Project）归档。`viking://user/` 缺少自动从编码交互中提炼**个人偏好（Persona / Preferences）**的认知管道（Cognitive Pipeline）；
2. **缺乏个性化与项目记忆的冲突消解：** 当用户的全局偏好（例如“始终优先使用 Tailwind CSS 和 TypeScript 严格模式”）与某个维护中的老遗留项目（如纯 JS + SCSS）冲突时，OpenViking 缺乏优先级仲裁机制（Project Context 覆盖还是 Persona 妥协？）；
3. **缺少从拒绝行为（Negative Feedback）中学习的闭环：** 现有捕获管线仅在 `SessionEnd` 提取总结，无法捕获“用户在编辑时撤销了 Agent 的哪一行代码、打回了什么建议”，导致个人助手无法形成独特的“默契感”；
4. **Context Assembler 的 TypedQuery 丢失关键上下文：**
   ```text
   TypedQuery = query + context_type + intent + priority + target_directories
   ```
   主链路中 `expand_queries()` 丢失了 `context_type`（如区分这是针对 `user_preference` 还是 `project_fact` 的查询），导致多查询检索合并时无法保证个性化偏好的稳定前置。

这正是个人 Agent 助手的关键切入点：在 OpenViking 基础存储之上，构建专门面向个人开发者的**个性化偏好挖掘、冲突仲裁、隐式对齐与白盒演进网关**。

### 3.3 已有能力与本项目增量的边界

| 能力 | OpenViking 已有 | SagaContext 是否重复建设 |
|---|---:|---:|
| Session 创建、归档、提交 | 是 | 否，调用 sidecar |
| L0/L1/L2 分层内容存储 | 是 | 否，调用 sidecar |
| `viking://user/` 基础路径支持 | 是 (基础目录结构) | 否，在上层构建偏好提取与流动管道 |
| Codex/Claude Code 基础插件 | 是 | 只做薄适配与统一配置 |
| 开发者个人偏好（Persona）自动挖掘 | 否 | 是，主创新点（个性化核心） |
| 个人偏好 vs 项目事实的冲突仲裁 | 否 | 是，主创新点（多级作用域解析） |
| 基于用户拒绝/修改的隐式反馈学习 | 否 | 是，主创新点（个性化反馈闭环） |
| TypedQuery priority-aware 融合 | 当前不足 | 是，主创新点（偏好优先保真） |
| 个人工作流 Markdown 镜像与本地白盒干预 | 否 | 是，主创新点（白盒心智可控） |
| LongMemEval-V2 与工程持续学习评测 | 非项目目标 | 是，主创新点 |

## 4. 相关项目对照

### 4.1 Codex 原生记忆

OpenAI 官方文档将 Codex 本地记忆描述为独立的本地记忆存储，默认关闭，可通过配置启用。当前源码中的记忆流程分为两阶段：

- **Phase 1：** 从符合条件且已空闲的历史 rollout 中并行抽取 `raw_memory` 与 `rollout_summary`，带任务认领、并发限制、重试和秘密脱敏；
- **Phase 2：** 在全局锁下把阶段一产物整合到 `MEMORY.md`、`memory_summary.md`、rollout summaries 和 skills，并通过 Git diff 驱动内部本地整合 Agent。

Codex 还会从回答中的记忆引用统计 `usage_count` 与 `last_usage`，用于后续保留/整合排序；深层召回主要由本地文件搜索完成，而不是 Dense Retrieval。

可借鉴的是后台两阶段管线、全局串行整合、秘密脱敏、引用反馈和“记忆不是强制规则”的边界。缺口是 Codex 本地记忆不天然与 Claude Code 共享，也没有 OpenViking 的 `viking://` 分层上下文模型。

### 4.2 memU

memU 的 `MemoryService` 是 Embedding-only 服务，本身不调用 LLM。宿主适配器负责读取 Codex、Claude Code 等历史记录，外部 Agent 负责把结果写成 Markdown、Skill 或资源，再由服务完成存储、Embedding 和召回。

在线 `progressive_retrieve()` 的路径是：

1. Query 只做一次 Embedding；
2. 召回 segment；
3. 将 segment 上卷到 file；
4. 并行召回 workspace resource。

该设计对本地隐私和成本友好，但当前没有意图路由、Sparse Retrieval、Rerank 或充分性判断。SagaContext 可以借鉴其“宿主适配器与记忆服务分离”以及“Agent 负责语义整合”的边界。

### 4.3 Mem0

Mem0 是通用记忆库，不是 Coding Agent 专用系统。当前主线强调：

- 单次 ADD-only 抽取，避免在写入时直接 UPDATE/DELETE；
- Agent 确认的事实可作为一等记忆；
- Entity Linking 用于跨记忆关系和召回加权；
- Semantic、BM25 和 Entity 多信号并行计算并融合；
- 可选 LLM、HuggingFace、Sentence Transformer 等 Reranker；
- 支持 user/agent/run 等作用域和记忆历史。

它证明“Dense + Sparse + Entity + Rerank”已经是成熟通用能力。因此 SagaContext 不应把“增加 BM25 或 Rerank”单独宣传为创新，而应研究这些信号如何与 TypedQuery 的优先级、Coding 记忆类型及证据可靠性共同作用。

### 4.4 memsearch

这是最直接的竞品。它已经覆盖：

- Claude Code、Codex 等多宿主共享记忆；
- Markdown 为事实源，Milvus 为可重建 shadow index；
- Dense + BM25 + RRF（默认 `k=60`）；
- Search -> Expand -> 原始 Transcript 的三级展开；
- PROJECT/USER 长期摘要；
- 从重复工作中提炼 Skills。

因此“Coding Agent + Hybrid Search + RRF + 双插件”不足以区分本项目。SagaContext 的差异应放在 OpenViking 分层上下文、TypedQuery 语义保真、证据可追溯和统一实验协议。

### 4.5 Letta Code

- **背景与定位：** 源自 UC Berkeley 的 MemGPT 论文体系，将 LLM 视作 CPU，将有限上下文视作 L1/L2 Cache。Letta Code 是完整的 Stateful Agent Harness，而不只是记忆库。
- **技术路线：**
  - 分层内存结构：分为始终注入的 Core Memory（包含 system, persona, human, project 块，支持 Agent 自主调用 API 修改）与按需分页召回的 Recall Memory / Archival Memory；
  - 提供可编程重写 Memory Blocks、Skills、Prompt 和 Mods；
  - 基于 Git-backed MemFS 实现记忆上下文版本化；
  - 提供 `/search` 消息检索、`/doctor` 记忆审计和 `/sleeptime` dreaming 整理机制；
  - 支持 Agent 之间和多渠道之间共享状态。
- **权衡与启示：** 启发在于把“始终注入的小型常驻索引”和“按需召回的深层经验”分开，以及记忆纳入版本控制。其代价是高度侵入 Agent 执行循环（接管了 Agent Harness），无法作为轻量插件赋能原生 Claude Code 或 Codex。SagaContext 应保持 Gateway + 适配器 + 编排层的边界。

### 4.6 Cline / Roo Code (Memory Bank 范式)

- **背景与定位：** Cline / Roo Code 是 VS Code 侧边栏的自主 Coding Agent。针对长会话上下文超限和多会话失忆问题，社区提炼出了 **Memory Bank** 协议，定位为**纯文本、去中心化、开发者白盒自维护的项目级知识契约**。
- **技术路线：**
  - 静态文件契约：在项目根目录强制建立 `memory-bank/` 目录，划分为 `activeContext.md`（当前工作焦点与变动）、`productContext.md`（项目目标）、`systemPatterns.md`（架构设计模式）、`techContext.md`（技术栈约束）、`progress.md`（进度看板）；
  - 生命周期闭环：任务初始化时全量读取 Memory Bank 引导上下文；任务收尾前通过 System Prompt 强制要求 Agent 自反思更新（Self-Update）Markdown 文件。
- **权衡与启示：**
  - *优点：* 完全透明可读、零额外向量库依赖、天然纳入 Git 进行版本管理和 Code Review；
  - *缺点：* 消耗大量 Token，完全依赖 LLM 遵从性（易发生遗忘更新或胡乱改写），缺乏细粒度的向量/BM25 检索能力；
  - *对 SagaContext 启示：* SagaContext 底层使用 OpenViking 保证高精度的检索与 Token 预算，但在交互上可提供 Memory Bank 导出的 Markdown 镜像，保障开发者白盒掌控感。

### 4.7 Zep / Graphiti (时序知识图谱范式)

- **背景与定位：** Zep 针对传统向量数据库“无法处理随时间演进的矛盾事实”痛点开发的开源引擎（`graphiti-core`），定位为**时序感知的动态实体关系记忆层**。
- **技术路线：**
  - Bi-temporal 图模型：将记忆抽取为实体（Entity）与有向边关系（Relation）；
  - 边失效机制（Edge Invalidation）：每条边携带 `valid_at`、`invalid_at` 及 `superseded_by` 属性。当新事件引入与旧事实冲突的决策时，自动将旧边标记为已废弃，并建立演进链接；
  - 混合图检索：结合社区检索、BFS 扩散和节点向量相似度，支持历史时间旅行（Time-travel）查询。
- **权衡与启示：**
  - 软件开发本质上是强时序演进的（以 Git Commit 为时间轴）。传统向量检索极易召回高相似度的“过时废弃代码/架构”，产生致命的负迁移（Negative Transfer）；
  - SagaContext 应在数据模型中吸收其时序覆写思想（`superseded_by`），在 Weighted RRF 中引入时效性衰减与失效阻断。

### 4.8 SWE-bench-CL 与 LongMemEval-V2 (评测基准体系)

- **LongMemEval-V2：**
  - 包含 451 个手工问题、5 类能力（静态回忆、动态跟踪、流程知识、环境陷阱、前提意识）、最多 500 条多模态轨迹、约 115M tokens haystack；
  - 针对通用 Agent 轨迹，重点评测准确率、查询延迟和 LAFS（长程上下文保真）。
- **SWE-bench-CL (Continual Learning for Coding Agents, 2025)：**
  - **背景与定位：** 传统 SWE-bench 是无状态（Stateless）单次解题，而真实工程是持续演进的。SWE-bench-CL 专为评估 Coding Agent 在连续多任务、跨 PR 过程中的记忆留存与复用能力而设计；
  - **核心指标：** 正向知识复用（Forward Transfer，是否因积累经验而减少探索 Token/步数）、抗遗忘与无回归（Backward Transfer / Regression Resistance，避免引入新记忆搞坏已有功能）。
- **评测策略落地：** SagaContext 采用“LongMemEval-V2 做通用长程检索标尺 + SWE-bench-CL/代码任务切片做工程场景标尺”的双重闭环。

## 5. 三条路线比较

### 路线 A：独立 Policy Gateway（推荐）

OpenViking 继续承担存储、Session、分层内容和基础召回。SagaContext Gateway 负责：

- Query Planner 结果标准化；
- TypedQuery-aware Weighted RRF；
- URI/证据去重；
- Coding 记忆类型过滤和项目作用域；
- Token budget、分类配额和 detail tier；
- 证据引用和检索 trace；
- LongMemEval-V2 与 Coding 任务评测。

Codex 与 Claude Code 各自只保留宿主 Hook、Transcript 解析、项目 ID 计算和 Gateway 调用。深层内容仍通过 OpenViking MCP `read/search` 获取。

**优点：** 创新边界清楚；可独立评测和发布；不需要复制 OpenViking AGPL 服务端；可以逐步替换排序策略。  
**代价：** 本地安装多一个 Gateway 进程；需要维护两套宿主输入格式。

### 路线 B：直接修改 OpenViking

直接在 OpenViking 的 Context Assembler 内保存 TypedQuery，并实现 priority-aware Weighted RRF，再修改上游插件和测试。

**优点：** 调用链最短；容易做成上游 PR；没有额外网络跳转。  
**代价：** 成果更像上游功能补丁；与 OpenViking 服务端代码耦合；项目独立性与许可证边界更复杂；需要跟踪上游变更。

### 路线 C：纯 Skill/Agent 编排

不增加 Gateway，只通过 Skill 让模型主动调用 `find/search/read/remember`，自行判断意图、证据和预算。

**优点：** 初始开发量最小；可快速演示。  
**代价：** 依赖模型是否选择调用工具；延迟和 Token 不稳定；难以做严格排序和无回归评测；无法保证隐私过滤与作用域策略在每次调用都一致。

### 路线结论

首版采用**路线 A**。路线 B 可作为后续向 OpenViking 贡献的实验分支，路线 C 只作为无 Gateway 的基线，不作为主实现。

## 6. 推荐架构

```text
Codex Hook ───────┐
                  ├─> Host Adapter ─> SagaContext Gateway ─> OpenViking sidecar
Claude Code Hook ─┘          │                 │                  │
                              │                 ├─ Query/Policy    ├─ viking://
                              │                 ├─ Weighted RRF    ├─ Session
                              │                 ├─ Evidence Ledger ├─ L0/L1/L2
                              │                 └─ Budget Renderer └─ MCP read/write
                              │
                              └─> Eval Runner ─> LongMemEval-V2 / Coding set
```

### 6.1 Host Adapter

每个宿主适配器负责：

- 接收 SessionStart、UserPromptSubmit、Stop、PreCompact、SessionEnd 等事件；
- 解析宿主的 Transcript 和 Tool 轨迹；
- 计算稳定的 `project_id`、`session_id` 和 `source_agent`；
- 将原始事件交给本地 Gateway，不在 Hook 内实现检索策略；
- 对 Gateway 超时或不可用采用 fail-open，不能阻塞编码任务。

OpenViking 现有 Codex/Claude Code 插件可作为事件格式和安装行为的参考；SagaContext 只保留薄适配层，避免重复实现其完整记忆插件。

### 6.2 Gateway

推荐 Python + AsyncIO，监听本机 `127.0.0.1`，提供内部 HTTP API；OpenViking 仍通过 HTTP/MCP 访问。核心模块：

1. `scope`：项目、用户（User Persona）、Agent、Session 多级隔离与仲裁；
2. `preference_miner`：基于多轮交互、代码 Rollback/Reject 反向挖掘个人习惯，区分显式约束与隐式偏好；
3. `capture`：异步队列、批量提交、重试和秘密脱敏；
4. `planner`：保留 TypedQuery 全字段并记录 planner 输出，注入个性化意图；
5. `retrieval`：并发召回、Weighted RRF、URI 去重和可选 Rerank；
6. `evidence`：维护命中 URI、来源 Session、原始消息/Tool 轨迹定位；
7. `budget`：L0/L1/L2 选择、分类配额（优先保留个人 Persona 配额）、总 Token 上限和降级；
8. `render`：生成带 URI、偏好标签和证据元数据的注入块；
9. `mirror`：双向同步 Markdown 镜像文件，支持本地 CLI（`sagactl`）白盒干预；
10. `eval`：离线重放、指标汇总和实验配置锁定。

### 6.3 Weighted RRF 设计

首版不直接融合不可比较的原始 Dense/BM25 分数，而使用排名融合。对候选 URI `u`：

```text
score(u) = Σ_i w(query_i) / (k + rank_i(u))
```

其中：

- `query_i` 是一个 TypedQuery；
- `rank_i(u)` 是 URI 在该查询结果中的名次；
- `k` 是可配置常数，默认先与 memsearch 的 `k=60` 对照；
- `w(query_i)` 由 `priority`、`context_type`、`purpose` 和实验配置确定；
- 同一 URI 的多次命中累加，而不是只保留最高原始分数。

首版必须输出每个候选的分解信息：命中的 query ID、各 rank、权重、RRF 子分数、最终分数、去重原因和降级原因。这样才能解释 Recall 改善来自哪里，并支持消融实验。

### 6.4 个性化分层数据模型与多级作用域

针对“个人开发助手”的核心诉求，系统建立三级作用域（Scope Hierarchy）：
1. **`User Scope` (`viking://user/...`)：** 跨项目全局有效。存储个人通用偏好、习惯工具链、代码格式习惯、对话风格预期、常用技术栈模板等；
2. **`Project Scope` (`viking://project/<proj_id>/...`)：** 单代码库内有效。存储该项目的架构决策、依赖约束、环境坑点、模块职责划分；
3. **`Session Scope` (`viking://session/<session_id>/...`)：** 单次会话生命周期。存储临时探索上下文与未合并的代码变更。

建议单条记忆在 Gateway 中维护的数据模型如下：

```text
memory_id
scope                     # user / project / session（三级作用域）
context_type              # memory / resource / skill
memory_kind               # preference/decision/constraint/failure/workflow/convention
source_agent              # codex/claude-code
session_id
source_uri                # viking://user/... 或 viking://project/...
source_turn_ids           # 原始轨迹定位
git_root / git_revision   # 项目上下文（若为 user 偏好则为空或通配）
affected_paths            # 关联的文件路径列表（代码邻近度锚定）
symbol_anchors            # 关联的核心类/函数/AST符号
temporal_status           # active / stale / superseded（时序有效性状态）
superseded_by             # 被哪条新记忆 URI 废弃取代
personal_signal           # explicit_pin / implicit_mined / rejected_correction
user_sentiment            # preferred / disliked / neutral
confidence
created_at / updated_at
supersedes / related_uris
redaction_status
```

#### 偏好与项目事实的冲突仲裁策略（Resolution Matrix）
- **规范与风格（Style & Convention）：** 优先遵循 Project Scope（“入乡随俗”；若项目已定义 eslint/prettier 则覆盖用户全局格式习惯）；
- **工作流与交互习惯（Workflow & Interaction）：** 优先遵循 User Scope（如“解释代码时简短说明”、“优先输出单测”，不受项目变动影响）；
- **库选型与架构（Libraries & Stack）：** 严格以 Project Scope 为准，禁止将用户对新技术的全局狂热强加给遗留项目。

#### 时序有效性与防负迁移
不同 Git 仓库默认隔离；同一仓库的 Codex 和 Claude Code 共享项目命名空间。用户偏好放在独立全局命名空间，不自动混入项目记忆。对处于 `superseded` 状态的废弃记忆，检索层默认做阻断过滤；对代码发生重大变动（Git Diff 重叠）的条目，引入时序衰减（Temporal Decay）以防止毒性负迁移。

### 6.5 证据注入与个性化 Prompt 渲染

检索结果分为三层，并对个性化记忆实行差异化渲染：

1. **L0：** URI、类型、简短摘要和置信度，用于低成本候选筛选；
2. **L1：** 决策/约束/流程的可读概览；
3. **L2：** 原始 Session、消息、Tool 轨迹或文件片段，仅在需要时读取。

**个性化 Prompt 渲染契约：**
在装配最终 Prompt 时，Gateway 划分固定配额空间：
- **`[Personal Persona & Constraints]`（强配额，常驻/高优先级召回）：** 提取自 `viking://user/` 的高频强偏好（如 `<user_preference type="style">...</user_preference>`）；
- **`[Project Architectural Context]`（按需召回）：** 提取自 `viking://project/` 的近期架构决策；
- **`[Historical Pitfalls & Failures]`（按需召回）：** 与当前修改文件强相关的踩坑与踩雷警告。

注入内容必须携带来源 URI，且不能让记忆正文伪造外层标签。需要深挖时，Agent 通过 MCP `read` 回到原始内容。Gateway 记录“召回了什么、注入了什么、最终回答引用了什么”，但不把完整原始 Transcript 默认塞进每轮 Prompt。

### 6.6 本地白盒控制：双向 Markdown 镜像与人机纠偏

为消除开发者“黑盒失控”的焦虑，Gateway 实现类似 Cline Memory Bank 的白盒投影：
- **只读 Markdown 投影：** 定期将 `viking://user/` 导出为 `~/.config/sagacontext/user_persona.md`，将当前项目记忆导出为 `.saga/project_context.md`；
- **开发者 CLI 纠偏命令：**
  - `sagactl pin <memory_id>`：将某条偏好升格为永久常驻记忆（类似 Windsurf Pin）；
  - `sagactl revoke <memory_id>`：当 Agent 误学了错误偏好时，一键拉黑废弃；
  - `sagactl review`：进入交互式审核终端，快速扫描最近自动挖掘出的用户偏好列表。

## 8. 评测设计

### 8.1 基线

至少保留以下方法：

1. `NoMemory`：不注入历史记忆；
2. `FullHistory`：按固定规则注入全量历史或长摘要；
3. `OpenVikingNative`：只使用 OpenViking 原生 Context Assembler；
4. `OV+RRF(no priority)`：接入 Gateway，但不使用 TypedQuery priority；
5. `SagaContext-RRF`：保留 `context_type` 和 `priority` 的 Weighted RRF；
6. `SagaContext-RRF+Rerank`：在固定候选池上增加 Reranker。

### 8.2 指标

**检索层：** Recall@5/10、MRR、nDCG、候选去重率、证据引用 Precision/Recall。  
**回答/任务层：** LongMemEval Accuracy、Coding 任务成功率、错误修复后的无回归率。  
**效率层：** Gateway 查询 P50/P95、OpenViking 查询 P50/P95、Memory Prompt Token、捕获队列积压和失败率。  
**安全层：** Secret redaction 命中率、跨项目泄漏测试、越权 URI 访问测试。  
**整体比较：** LongMemEval-V2 的 Accuracy/Latency/LAFS，以及 Coding 任务的质量/延迟/Token Pareto frontier。

### 8.3 实验控制变量

每次实验必须固定并记录：

- Reader/Planner/Embedding/Reranker 模型和版本；
- OpenViking commit、Gateway commit 和配置；
- `k`、TypedQuery 权重映射、Top-K、detail tier、Token budget；
- CPU/GPU、并发度、请求超时和重试；
- 缓存冷热状态；
- 数据集版本、样本顺序和随机种子；
- 是否包含原始 Tool 轨迹和图片。

### 8.4 原草稿数字的处理

以下数字只能作为首版实验目标或占位，统一标记为 `[TARGET]`/`[VERIFY]`：

| 原草稿说法 | 报告中的正确状态 |
|---|---|
| 80 条跨会话 Coding 任务 | `[TARGET]` 固定任务集规模，尚未完成实验 |
| 输入 Token `1.8 万 -> 1.1 万` | `[TARGET]` 约 39% 降幅，需在同一模型/上下文策略下重测 |
| Recall@10 `69% -> 75%` | `[TARGET]` +6pp，需证明来自 priority-aware 融合 |
| P95 `0.29s -> 0.31s` | `[TARGET]` 约 +7%，需区分 Gateway、OpenViking 和模型开销 |
| Accuracy `54% -> 64%` | `[TARGET]`，需在 LongMemEval 版本和固定 reader 下重测 |
| Memory Prompt Token `2.0 万 -> 0.9 万` | `[TARGET]` 约 55% 降幅，需报告截断和 detail tier 规则 |

工程验收建议优先采用约束式门槛，而不是预先承诺提升值：质量必须有可重复的正向信号；检索延迟增幅控制在实验允许范围内；Coding 任务成功率不得出现不可接受的回归；跨项目和秘密泄漏测试必须为零容忍。

## 9. 隐私、可靠性和许可证风险

### 9.1 本地隐私边界

- 默认只连接本机 Gateway 和本机 OpenViking；
- 用户配置的 LLM/Embedding/Reranker 服务仍可能收到必要文本，必须在配置和日志中显式标注；
- Secret redaction 发生在写入和发送外部模型之前；
- 原始 Transcript 默认只保留引用和按需读取，不默认全量进入 Prompt；
- 记忆正文视为不可信外部上下文，必须有 URI/来源约束；
- 提供按项目删除、按 Session 删除和完整 reset；
- 调试日志默认不记录 Token、密钥和完整代码片段。

### 9.2 许可证边界

OpenViking 当前为 AGPL-3.0；Codex、memU、Mem0、Letta Code 和 LongMemEval-V2 为 Apache-2.0；memsearch 为 MIT。该报告不是法律意见。工程上建议：

- 将 OpenViking 保持为独立 sidecar；
- 通过其 HTTP/MCP 接口调用；
- 不复制或修改其 AGPL 服务端代码作为 SagaContext 的核心库；
- 对采用上游插件代码的部分保留来源与许可证声明；
- 在发布前由项目维护者确认最终分发方式和许可证兼容性。

### 9.3 故障策略

- 召回超时：跳过记忆注入，继续当前编码任务；
- 捕获失败：写入本地 pending queue，指数退避重试；
- OpenViking 不可用：CLI `doctor` 报告，宿主 Hook 不阻塞；
- Planner 输出非法：回退到原始用户 Query；
- Reranker 失败：回退 Weighted RRF；
- 证据不完整：降低置信度或只注入 URI/L0，不伪造完整结论。

## 10. 命名建议

### 首选：SagaContext

- `Saga` 表达跨 Session 延续的开发经历和决策链；
- `Context` 比 `Memory` 更准确，强调它是编排层而非数据库；
- 与 OpenViking、Codex、Claude Code 的产品名没有直接混淆；
- 本轮对 `sagacontext` 做了初步精确检查：GitHub 仓库搜索为 0，PyPI 和 npm 均未发现同名包。

建议命名层级：

```text
Repository: sagacontext
Python package: sagacontext
CLI: sagactl
Gateway service: sagacontext-gateway
```

这不是商标、域名或完整生态冲突结论。`SessionWeave` 和 `ContextLedger` 本轮发现已有包/项目占用，不建议作为首选；`CodeSaga` 的 GitHub 名称搜索结果较多，也不建议直接使用。
