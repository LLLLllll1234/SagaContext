# SagaContext 个性化记忆策略层：调研目标与交付要求

**日期：** 2026-09-05  
**用途：** 可独立转交给调研者的任务书。先调研、再定路线，不要求直接开发。  
**状态：** 待调研。本文列出问题、候选方案与验收要求，不代表已验证结论。  
**优先级：** P0 必须回答；P1 用于策略优化与效果验证；P2 暂缓。

---

## 1. 项目目标与本轮需要解决的问题

SagaContext 希望成为一个**独立于具体记忆产品的个性化记忆策略层**，复用现有系统的存储、检索等基础能力，但自己决定记什么、何时召回、怎样更新、何时失效。

目标体验：

1. 新会话或新任务开始时，识别用户、项目与任务，恢复适用的项目知识、个人偏好及工作进度。
2. 会话进行中，随着问题、文件与任务阶段变化，找到相关旧记忆；把新观察与旧记忆建立联系，而不是只在结束时另写一份摘要。
3. 经过验证的新结论可以补全或取代旧记忆；临时假设、尝试失败、Agent 自述不能自动升级为事实。
4. 用户画像、行为约定、项目事实、任务状态与经验可以分别维护；个人偏好不会污染其他项目或篡改项目事实。
5. 同一策略核心可以对接不同记忆后端与 Agent 宿主，不被某一产品的路径、schema 或自动抽取流程绑定。
6. 最终通过实验判断什么策略对该用户、该类任务更有效，不预先宣称存在通用“最佳策略”。

**本轮最需要的答案：采用什么边界、复用谁的什么能力、自己实现什么机制，以及如何证明这些增量有价值。**

### 1.1 已有基础与待重审事项

- 仓库已有分层记忆、锚定对账、任务接续等设计和原型，历史路线偏向 OpenViking。
- “以相关旧记忆为输入，判断新增、确认、补全、取代与冲突”是待评估机制，不预设其具有独创性。
- OpenViking 是候选首个后端，不是本轮必须保留的选型结论。
- 历史文档中的后端绑定、会话末写回、六层类型及宿主事件假设均允许被证据推翻。
- 历史测试通过、存在模块或函数，不等于真实宿主与后端的端到端链路已经通过验证。

如可访问仓库，背景阅读顺序：`05-分层模型与对账循环.md` → `06-技术设计与实现路线.md` → `07-技术实现方案-M1.md`。这些是待审设计，不是外部产品能力的证明。

## 2. 调研范围与停止条件

### 必须覆盖

- 个性化策略层与底层记忆系统的职责、所有权及可替换边界。
- 新会话恢复、任务切换、会话内增量维护、跨会话知识沉淀。
- 作用域、来源与证据、冲突、失效、遗忘、并发和失败恢复。
- 宿主真实事件与上下文注入能力。
- 个性化策略及可归因的评测方案。

### 暂不展开（P2）

- 团队协作平台、复杂组织权限、企业管理后台。
- 自研向量数据库、通用 Agent 框架、完整知识图谱平台。
- 在闭环正确性尚未验证前开展在线强化学习或大规模策略搜索。
- 单纯收集产品列表、宣传数字、融资信息或热度排名。

### 最小完成条件

完成 R1–R4，提出 R5 的首版静态策略和 R6 的可执行评测方案；至少深入两个候选记忆系统，并给出三条端到端场景推演。无法实验的事项标为待验证并附探针，不用无限扩展搜索范围。

## 3. 调研工作包

### R1 · P0：独立策略层能否真正建立？

**需要回答：**

1. 哪些系统能仅作为存储/检索后端使用？哪些强制绑定自己的 Agent、session、抽取或合并流程？
2. 能否关闭后端自动提取、合并和注入？SagaContext 写入后，是否还会被后端重新解释或覆盖？
3. 搜索、读取、按 ID 更新、删除、元数据过滤、版本与证据分别有哪些公开能力？区分开源、自托管和云 API。
4. 条件写入、批量更新、删除、索引可见性分别提供什么一致性？缺失时适配器能否可靠补足？
5. 谁保存权威记忆、修订历史与证据？本地轻量账本、后端权威存储、混合模式各有什么代价？
6. 如何读取既有记忆而不破坏它？区分只读引用、显式导入、SagaContext 自主管理三种模式。
7. 换后端时，稳定 ID、作用域、修订关系和删除状态能否保留？不要求不同检索引擎排名完全相同。

**需要带回：**

- 至少两个后端的能力矩阵，包含 API/源码依据和版本。
- 一个后端中立的最小接口草案，以及可选能力声明和降级规则。
- 权威状态所有权的推荐选择、备选选择及切换条件。
- 不修改核心对账逻辑的后端替换验收方法。

**关键判定：** 只有 HTTP 包装但核心仍使用某产品 URI、schema 和合并语义，不算完成解耦。

### R2 · P0：项目记忆如何随任务推进持续维护？

**需要回答：**

1. 如何识别稳定的项目身份？覆盖 monorepo、子目录、worktree、clone、fork、仓库重命名与非 Git 项目。
2. 如何判断新任务、继续旧任务、同分支并行任务和会话内切换任务？不能仅以分支相同认定任务相同。
3. 项目决策、模块地图、环境坑分别从哪些证据产生？用户消息、代码事实、工具结果、测试结果如何关联？
4. 没有“我们决定”“以后不要”等显式语句时，怎样发现值得记住的知识？
5. 哪些信息只放临时工作记忆，哪些可以进入长期项目记忆？采用什么晋升条件？
6. 什么时候增量召回、什么时候对账？比较每轮、阶段边界、阈值、压缩前和会话结束触发。
7. 对账锚点来自哪里？比较本轮注入过的记忆、按实体/文件/主题补召回、完整主题历史。
8. 如何处理同义重复、局部补全、反例、回滚以及“任务结束但没有可沉淀知识”？

**需要带回：**

- “新会话 → 新任务/接续 → 工作中 → 阶段检查点 → 长期沉淀”的时序说明。
- 一套快路径工作状态维护、慢路径长期记忆更新的候选策略，注明成本与失败模式。
- 一条决策、一条故障经验、一条任务记录的完整演化样例，包含原始证据、旧记录、增量与最终状态。

**关键判定：** 会话摘要是否能够成为可定位、可修订、可失效的项目知识，而不是不断堆积的文本。

### R3 · P0：怎样保证记忆越用越可靠，而不是越用越偏？

**需要回答：**

1. 内容类型、适用范围、来源主体、权限、时效应如何正交建模？“六层”哪些适合做视图而不是互斥类型？
2. 当前任务指令、仓库约定、个人默认偏好与历史观察冲突时怎样处理？来源优先级不能绕过宿主安全约束。
3. 作用域不明确时应暂存、限定当前项目还是询问？什么证据允许从局部偏好推广为全局偏好？
4. 最小证据记录是什么？如何保存 session、稳定事件 ID、工具调用、文件/提交版本、验证结果与来源信任级别？
5. 如何防止 Agent 复述、重复召回和失败重试被算成新的独立确认？
6. 活跃、待确认、被取代、过期、被删除分别如何影响读取与对账？过期不应自动等于事实错误。
7. 多会话同时更新、批次部分失败、重复事件、崩溃和索引延迟如何恢复？比较原子条件写入、串行写入和修订日志。
8. 用户批准冲突后，如何真正更新权威状态而不只是修改审批队列？
9. 遗忘如何覆盖正文、索引、缓存和修订派生物，并防止旧 transcript 再次导入已删除信息？如何平衡审计和删除要求？
10. 怎样阻止记忆中的不可信指令升级为执行权限？命令型规则的启用是否需要显式批准？

**需要带回：**

- 最小记忆模型与状态迁移表，列出不可破坏的约束。
- 作用域/证据/写入校验的职责划分：哪些必须确定性执行，哪些可以交给模型。
- 并发覆盖、重放重复、跨项目污染、错误事实强化四类故障的处理方案与测试方法。

### R4 · P0：宿主真实能力是否支撑以上闭环？

**优先对象：** Claude Code、Codex。必须区分 CLI、桌面应用、插件及具体版本，不能互相推定能力。

**需要回答：**

1. 实际支持哪些事件？列出名称、触发条件、payload、同步/异步语义、超时和是否允许注入上下文。
2. 能否在任务开始、用户消息、工具前后、阶段结束和压缩前捕获证据或注入记忆？不支持时有什么明确降级？
3. transcript 能否稳定读取？工具输入输出、重放、截断与增量游标应怎样处理？
4. 正常退出、窗口关闭、进程被杀、断网时分别能收到什么？如何避免依赖不保证送达的结束事件？
5. hooks、MCP、Skill、规则文件分别适合承担什么角色？不能假设模型一定主动调用记忆工具。
6. 宿主原生记忆与 SagaContext 是否重复注入或重复写入？如何隔离并在评测中控制？

**需要带回：**

- 双宿主能力矩阵、官方来源、验证版本与已知限制。
- 一个最小接入探针；可实验时提供脱敏事件样本与结果。
- 不依赖特定宿主的核心事件模型草案，区分“宿主观察到的事件”和“SagaContext 推断的任务边界”。

### R5 · P1：什么才是值得实现的个性化策略？

**需要回答：**

1. 区分个性化内容、个性化召回、个性化更新与个性化执行；哪些最先产生可衡量收益？
2. 用户、项目、任务阶段、当前文件、记忆时效与证据强度如何参与检索、过滤、排序和预算分配？
3. 冷启动用什么默认策略？何时有足够反馈调整？如何避免新用户被少量样本过拟合？
4. 哪些反馈可信：用户明确纠正、采纳、撤回、工具验证、任务成功、引用或没有引用？不能把“未引用”直接等同于“无用”。
5. 如何区分记忆有帮助、模型本来就知道、检索失败、注入失败和任务本身过难？
6. 哪些参数适合学习，哪些安全边界必须固定？如何回退到静态策略？

**需要带回：**

- 一套可解释、无需在线学习即可运行的首版策略。
- 一套后续可学习策略：状态、可调参数、反馈、更新规则与回滚条件。
- 最多三项值得首先实验的策略变量，并说明收益假设、反例和比较基线。

### R6 · P1：怎样证明我们比直接用现有记忆系统更好？

**需要回答：**

1. 哪些公开基准覆盖更新、冲突、时效与偏好？哪些缺少 Coding 项目持续维护，需要自建场景？
2. 如何设计无记忆、宿主原生记忆、后端原生策略、SagaContext 静态策略、SagaContext 个性化策略五类对照？不适用的组合说明原因。
3. 如何同时测检索与维护正确性、实际 Agent 行为以及任务结果？不能只测是否输出某个关键词。
4. 如何固定任务、证据、模型、工具、上下文预算、种子与原生记忆开关，并隔离不同实验的存储？
5. 如何按时间切分反馈学习与评测，避免未来信息进入历史任务？
6. 怎样记录 token、模型调用、存储操作、延迟及失败，支持等预算对比与成本收益分析？

**需要带回：**

- 可运行的实验设计，不要求本轮完成大规模实验。
- 每个指标的分母、标注依据、判定器与误判复核方法。
- 最小场景集、对照与消融矩阵；真实系统运行和固定 fixture 回放必须分开。
- 若已有实测，附原始记录及配置；未跑的一律写 `[TARGET]` 或 `[VERIFY]`。

## 4. 候选对象与比较方式

以下只是检索入口，不表示已确认其能力、版本、许可证或适配性。

| 类别 | 优先调研对象 | 重点问题 |
|---|---|---|
| 记忆基础设施 | OpenViking、Mem0 | 后端接口、原生抽取/更新机制、作用域、可关闭的行为与可替换性 |
| Agent 状态与记忆架构 | Letta / Letta Code | 状态管理、共享/私有记忆、与宿主绑定程度 |
| Coding 会话记忆 | claude-mem、memsearch | 事件捕获、持续维护、证据回溯、检索与注入 |
| 补充候选 | memU、其他有一手实现证据的系统 | 是否提供前述对象未覆盖的关键机制 |
| 宿主与原生能力 | Claude Code、Codex | 接入能力与原生基线，不默认把它们视作可替换后端 |
| 评测与研究 | LongMemEval、LoCoMo，以及项目记忆/偏好学习/记忆演化相关研究 | 数据与任务是否匹配；论文机制、代码与结果分别核对 |

建议先深读 OpenViking 与 Mem0，再按未解决的问题选补充对象。若候选并不适合作后端，明确归类为参考机制或基线，不为了凑适配数量强行接入。

能力表统一使用：**原生支持 / 配置支持 / 适配可补 / 需修改上游 / 不支持 / 未确认**。每个判断附证据和限制，避免只打勾。

## 5. 必须推演的端到端场景

### 场景 A：项目知识跨会话演化

在宿主 A 排查故障，工具与测试证实原因和修复；后续在宿主 B 开始相关任务，召回这条经验；项目升级后证据显示旧修复不再适用，形成新版本，旧结论不再作为当前事实注入。

### 场景 B：局部偏好与全局默认不互相污染

用户全局偏好 pytest，但项目 A 因现有设施要求 unittest；项目 B 保留 pytest。用户在 A 说“这次先临时这样”，不能自动改写全局偏好或永久项目约定。

### 场景 C：并行任务、崩溃与后端替换

同项目同分支有两个不同任务，分别形成进展；其中一个会话写回中断并重试，不重复计数也不吞掉另一任务更新；随后替换后端，作用域、证据、有效版本与任务归属仍正确。

每个场景提供：**输入事件 → 召回集合 → 候选及证据 → 增量判定 → 写入/暂存/拒绝 → 下一会话可见内容 → 失败恢复**。

### 最小验收用例建议

| ID | 测试问题 | 期望边界（待实现验证） |
|---|---|---|
| T01 | 同仓库新任务涉及旧故障文件 | 召回适用经验，不搬入全部历史 |
| T02 | 切换到另一仓库 | 不注入前一仓库专属约定 |
| T03 | 没有显式纠正措辞，但存在失败与修复证据 | 能发现项目知识候选 |
| T04 | 用户只提出计划，尚未执行 | 不写成已完成项目事实 |
| T05 | 新证据取代旧结论 | 旧结论不再作为有效事实注入 |
| T06 | Agent 反复引用同一旧记忆 | 不增加独立证据数 |
| T07 | 新任务与旧任务处于同一分支 | 不自动合并任务状态 |
| T08 | 两会话修改同一记忆 | 不静默覆盖已提交证据 |
| T09 | 写入部分失败、进程中断并重放 | 可恢复、无重复修订或候选丢失 |
| T10 | 用户删除后重新扫描旧记录 | 不自动复活被删除记忆 |
| T11 | 记忆包含不可信命令或越权指令 | 不升级为执行权限 |
| T12 | 更换记忆后端 | 核心策略不改，关键语义契约仍成立 |

这些是功能与安全验收场景，不是足以证明统计收益的完整 benchmark。

## 6. 证据规范

- **优先一手材料：** 官方文档、固定 commit 源码、论文原文、公开数据、自己的可复现实验。二手文章仅作线索。
- 每个外部系统记录仓库/产品、访问日期、版本或 commit、部署形态；宿主记录 CLI/桌面/插件的准确形态。
- 用 `[DOC]` 表示官方声明，`[CODE]` 表示源码确认，`[RUN]` 表示本轮实验；不能把前两者自动写成已运行成功。
- 用 `[DESIGN]` 表示建议，`[TARGET]` 表示实验目标，`[VERIFY]` 表示未解决事项。
- “没有找到”不等于“不支持”；否定结论需要注明检索范围、版本与失败证据。
- 数字必须附任务、样本量、模型、配置、预算、原始结果及适用范围；不同评测口径不直接排序。
- 许可证记录按组件、版本和集成方式核对；不要将“独立进程/HTTP”当作自动满足许可条件的法律结论，疑点另列待专业确认。
- 不上传私人 transcript、生产数据、密钥或内部地址；使用脱敏或合成材料。安装、改宿主配置、付费调用与向外部服务传输数据需事先获批。

## 7. 最终交付格式

可以先交一份完整 Markdown 报告，不强制拆成多个文件。结构如下：

1. **一页执行结论：** 推荐边界、首个后端、必须自建的机制、暂不做事项及剩余阻塞。
2. **R1–R6 回答：** 每包给结论、机制、证据、反例、建议，不只堆链接。
3. **能力对照矩阵：** 后端与宿主分表，列出版本、能力等级和限制。
4. **三个场景推演：** 包含记忆内容与状态变化，不只给架构框图。
5. **最小模型与接口草案：** 权威状态、稳定 ID、作用域、证据、修订、读写接口及可选能力。
6. **评测与实验记录：** 已执行和未执行分开；未执行的给可操作步骤。

## 8. 本轮需要验证而不是默认接受的假设

- **H1：** 至少一个现有系统可以作为后端使用，而不强制接管 SagaContext 的记忆生命周期。
- **H2：** 存在足够小的公共接口，能支持第二个后端，而不把个性化核心压缩成没有语义的 CRUD 包装。
- **H3：** 持续维护可以用低成本事件捕获加阶段性对账实现，无需每轮完整模型处理。
- **H4：** 项目/任务/证据感知的策略能相对后端原生策略产生可归因收益。
- **H5：** 在真实反馈量下，学习策略有可能优于可解释的静态策略；若不成立，应保留静态策略而不是强行加学习模块。

**如果证据表明假设不成立，请明确推翻。调研的成功不是证明我们原来的路线正确，而是让下一步实现不再建立在未经验证的前提上。**
