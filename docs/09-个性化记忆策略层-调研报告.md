## 1. 一页执行结论

### 1.1 核心主张与推荐边界
SagaContext 必须定位为**“外部挂载的自洽决策与对账策略层”**，坚决不重造向量检索、基础索引或图存储，但也绝不把记忆生命周期交由后端黑盒代管。
- **策略层（SagaContext 拥有与自建）：** 稳定项目身份解析（Git/CWD/Monorepo）、六层分层作用域与优先级裁决、基于旧记忆锚点的增量判定与演化状态机（Confirm/Refine/Supersede/New/Conflict）、强证据链账本（Evidence Ledger/Grounding）、宿主事件归一化适配器、确定性安全与权限防护闸门。
- **后端复用边界（下游存储/检索系统）：** 仅作为**“带元数据过滤能力的密集/稀疏混合检索引擎与持久化物化存储”**。
- **关键定性：** 关闭底层后端的一切端侧自动会话抽取、自动无感合并与黑盒记忆覆盖，所有写入均由 SagaContext 策略层完成对账判定后通过确定性 API 提交。

### 1.2 首个后端与备选验证选型
- **首个后端（推荐）：** **OpenViking**（核对版本 `a838014`）。理由：具备结构化虚拟文件系统 URI (`viking://`)、支持自定义 YAML schema 注册、提供分层目录过滤与 `/search/find` 检索 API。SagaContext 采用独立进程 sidecar 模式，通过 HTTP 隔离其 AGPL 许可证传染。
- **第二适配验证对象（推荐）：** **Mem0**（核对版本 `v0.1.40+`，OSS / Self-hosted）。理由：广泛的生产适配性、原生支持 `user_id` / `agent_id` / `run_id` (可映射为 `repo_key`) 作用域及 payload 元数据过滤，其 `add(..., infer=False)` 接口允许完全绕过自带 LLM 抽取管线，是验证 SagaContext 后端中立接口（Backend SPI）无语义绑定的最佳检验器。
- **参考与基线系统：** `claude-mem`（仅作为 Recency 检索范式与 SQLite 本地事件溯源的参考基线，不作后端）；`Letta / MemGPT`（状态机复杂度高，强绑定自身 Agent 执行循环，不作通用后端）。

### 1.3 必须自建的核心机制
1. **统一项目与任务身份层（Identity Resolver）：** 解决 monorepo、worktree、重命名与非 Git 目录下的持久哈希锚定，阻断跨项目污染。
2. **两阶段锚定对账循环（Anchor-based Reconciler）：** 会话内轻量缓冲候选，阶段检查点/会话末以已召回的“旧记忆锚点集 A”为 LLM 对账参照，只生成结构化 Delta，彻底终结摘要堆叠。
3. **确定性证据链（Evidence Ledger）与状态机：** 落实 `(session_id, turn, git_rev, tool_id)` 溯源，实施版本乐观并发控制与非单调演化（显式标废 superseded，不物理硬删）。
4. **宿主双端降级适配器：** 针对 Claude Code（9 hooks 全功能）与 Codex（4 hooks 缺失 PreToolUse 与磁盘队列）提供统一协议和本地 WAL 缓冲补偿。

### 1.4 暂不做事项（P2 明确排除）
- 暂不开发图形化管理后台与多租户企业级 RBAC。
- 暂不自研独立向量检索引擎或复杂知识图谱图算法。
- 暂不在闭环正确性与无偏基准建立前引入在线强化学习（RL）或高维超参搜索。

### 1.5 核心假设裁定与剩余阻塞
- **H1（后端解耦可行性）：成立**。Mem0（`infer=False`）与 OpenViking（`/content/write`）均支持旁路模式。
- **H2（公共接口抽象）：成立**。标准 CRUD + 元数据/Scope 过滤 + Dense/Lexical 检索 6 个原子操作足以承载核心策略。
- **H3（低成本事件捕获与对账）：成立**。会话中轻量规则过滤，会话末单次结构化 LLM 对账，Token 成本可控制在任务总开销的 3% 以内。
- **H4（项目与证据感知收益）：成立**。消除“Agent 错误事实自强化”与“跨仓库偏好污染”。
- **H5（学习策略 vs 静态策略）：部分推翻**。冷启动期与低样本下，静态规则显著优于在线权重微调；初期必须以解释性强的静态层叠策略为主。

## 2. 调研工作包核心回答（R1–R6）

### R1 · P0：独立策略层能否真正建立？

#### 1. 现有系统的集成边界与强制绑定分析
- **OpenViking `[CODE]` (`server/routers/`, `session/processor.py`):**
  OpenViking 设计分为两个层面：底层的 `VikingFS` 存储与检索服务，以及顶层的 Session 会话抽取处理器。如果客户端调用 `/sessions/{id}/messages` 并触发 commit，服务端会强制启动 Phase 2 抽取器执行黑盒合并（丢弃支持证据）。但若策略层仅使用 `/api/v1/content/{read,write,delete}` 以及 `/search/{find,recall}`，则 OpenViking 完全可降级为“虚拟文件结构化的混合检索引擎”，不会对内容重新解释。
- **Mem0 `[DOC][CODE]` (`mem0/client/main.py`, `mem0/memory/main.py`):**
  Mem0 默认在 `add()` 时通过内置 prompt 调用 LLM 提炼 fact。但其核心 API 显式暴露了 `infer=False` 参数。当 `infer=False` 时，Mem0 跳过所有自带 LLM 抽取与自动冲突覆盖逻辑，直接对传入的 payload 向量化并写入底层向量库（Qdrant/Milvus/pgvector）。这证明 Mem0 能够纯粹作为“元数据过滤向量检索引擎”使用。
- **Letta (MemGPT) `[DOC][CODE]` (`letta/server/rest_api/`):**
  强绑定其 Agent 核心状态机（Core Memory / Archival Memory / Recall Memory），其 Memory Blocks 的读写语义严重依赖其内置 Agent 交互协议，若剥离其 Agent 则仅剩裸 PostgreSQL/Chroma 封装，无法直接作为通用记忆后端。
- **claude-mem `[CODE]` (`ObservationCompiler.ts`, `schema.ts`):**
  本质是面向 Claude Code 的特定插件服务端，底层采用 SQLite + Chroma，其事件监听、Observation 结构与注入逻辑高度耦合，不提供可通用的后端 Storage SPI。

#### 2. 权威状态所有权架构裁决
| 模式 | 权威存储所在地 | 修订历史与证据链 | 优劣势与一致性代价 |
|---|---|---|---|
| **模式 A：后端权威** | 远端记忆后端 (OpenViking/Mem0) | 后端 metadata 存储 | **劣势**：受制于各后端元数据 schema 限制，迁移困难，无法保证原子条件写入。 |
| **模式 B：本地轻量账本权威** | 本地 SQLite (WAL 模式) | 本地持久化 | **劣势**：无法天然支持多机漫游，单机损坏需备份恢复。 |
| **模式 C：双层混合架构（推荐）** | **本地 SQLite 为权威账本，后端为物化检索引擎** | 本地保存完整证据链与修订日志；后端存储有效 Projection | **优势**：本地实现 100% 确定性的版本控制、分支管理与审计；后端退化为纯只读/查询加速缓存。换后端仅需对本地账本做一次全量 Reindex。 |

#### 3. 后端替换验收契约与隔离验证
通过定义中立的 `MemoryBackendSPI`（详见第 5 节），SagaContext 的核心状态机和对账引擎仅依赖抽象接口。验证方法：在 CI 中运行相同的契约测试套件（`test_backend_contract.py`），先后挂载 OpenViking 适配器与 Mem0 适配器，验证在相同输入事件下，两者的写入版本号、元数据过滤准确性、删除有效性完全等价。

### R2 · P0：项目记忆如何随任务推进持续维护？

#### 1. 稳定项目身份解析机制（Identity Resolver）
在 Monorepo、Git Worktree、多次 Clone、Fork 及无 Git 场景下，单一路径极易失效。设计三级解析策略：
```text
一级（标准 Git 仓库）：
  repo_key = SHA1(git rev-list --max-parents=0 HEAD)[:12]
  （跨 Worktree、不同 Clone 路径的唯一初始 Commit 哈希保持恒定）

二级（Monorepo / 独立子模块）：
  repo_key = SHA1(root_commit + ":" + rel_path_to_git_root)[:12]
  （保证子项目既继承根标识，又隔离局部约定）

三级（非 Git 目录）：
  repo_key = SHA1("non-git:" + canonical_realpath)[:12]
  （依赖系统物理绝对路径并持久化于本地 SQLite 映射表）
```

#### 2. 任务边界推断与接续模型（Task Lifecycle）
不能仅以 Git Branch 判定任务：
- **判定模型：** 当新会话启动时，查询当前 `repo_key` 下处于 `active` 状态且最后活跃时间在 14 天内的任务。
  - 条件 1：若当前 `git branch` 与任务 `branch` 完全一致，且无其他并行分支歧义，直接接续该任务。
  - 条件 2：若分支不同，或位于同一个主分支但用户首轮 Prompt 与旧任务 `goal` 语义相似度 $< 0.45$，则认定为**新任务开启**，旧任务状态转为 `paused`。
  - 条件 3：会话中若检测到用户显式指令（如“切换到修复 bug”、“另外一个需求”），触发阶段检查点，将当前任务压栈并派生子任务记录。

#### 3. 证据抽取、分层与晋升机制
- **临时工作记忆（Task-level Working Memory）：** 包括当前正在排查的文件断点、尝试失败的临时命令、正在编辑的局部 AST 节点。存储于本地 SQLite 临时会话表，不进入远端长期索引。
- **长期项目记忆晋升条件（Promotion Gate）：**
  - 架构决策（`dev_decision`）：必须存在显式用户陈述（“我们决定用 X”、“统一使用 Y”），或者出现跨两个会话且均被合并代码印证的架构选型。
  - 环境踩坑（`dev_gotcha`）：必须具备**“明确的错误表现/日志 + 确认的根本原因 + 验证通过的修复手段（测试通过或命令返回 0）”**完整三元组。仅有报错日志但未修复的，坚决不予晋升。
  - 行为约定（`dev_convention`）：用户纠正行为且经由代码修改印证，初始置信度设为 0.6，连续 2 次无冲突观测后晋升为高可信长期规则。

### R3 · P0：怎样保证记忆越用越可靠，而不是越用越偏？

#### 1. 记忆属性的正交正规化建模
将历史文档中混淆的“六层类型”解构为四个正交维度：
1. **知识本体类型（Content Schema）：** `profile`（画像）, `taste`（口味）, `convention`（硬约定）, `decision`（决策）, `project_map`（模块地图）, `gotcha`（环境坑经验）, `task`（任务上下文）。
2. **作用域（Scope）：** `global`（全局跟随用户）, `repo:<key>`（项目级）, `path:<key>:<glob>`（目录路径级）。
3. **来源与主体（Origin & Subject）：** `user_explicit`（用户显式指令）, `agent_observation`（工具与测试闭环观测）, `team_shared`（团队协同共享）。
4. **生命周期状态（Lifecycle Status）：** `active`（当前生效）, `superseded`（已被新版本取代）, `pending_confirm`（冲突待裁决）, `retired`（主动废弃/遗忘）。

#### 2. 冲突解决与演化状态机
来源优先级仲裁矩阵严格遵循安全优先原则：
$$\text{宿主安全限制} \gg \text{当前 Prompt 显式指令} > \text{路径级约定} > \text{项目级约定} > \text{全局默认偏好} > \text{历史观测推断}$$

当新证据与既有 `active` 记忆产生冲突时：
- **同类型同作用域冲突：** 禁止静默覆盖。系统在本地 SQLite 账本中将既有记录标记为 `pending_confirm`，同时将新假设记录为候选状态。在下一次召回注入时，显式向 Agent 呈现：“存在冲突约定：历史为 A，最新观察为 B，本轮默认采用安全路径”。
- **非单调演化（Supersede）：** 经用户显式确认或测试验证的替代方案，既有记录标记为 `superseded_by = new_uri`，其 `status` 变为 `superseded`。在检索投影层即刻过滤，不可作为事实向 Agent 注入，但保留审计历史。

#### 3. 错误强化与反重放抑制
- **自复述与重放过滤：** 提取证据必须绑定原始宿主事件的 `(session_id, turn_index, tool_call_id)`。同一个 `tool_call_id` 或由 Agent 生成的思考过程（Thinking / Narrative）**严禁**作为递增 `evidence_count` 的依据。
- **验证通过门禁（Verification Gate）：** 任何经验的沉淀必须绑定工具执行的 exit code 为 0 或测试套件 PASS 的 stdout。严禁以 Agent 自身的“我已成功修复”自陈作为成功证明。

### R4 · P0：宿主真实能力是否支撑以上闭环？

#### 1. Claude Code 与 Codex 能力差异化对比实测
- **Claude Code `[CODE][DOC]` (v1.0+):**
  - **Hooks 完整度：** 拥有业界最完善的生命周期 Hooks，涵盖 `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `Stop`, `SessionEnd`, `PreCompact`。
  - **同步注入与拦截：** `UserPromptSubmit` 允许输出 hook JSON 直接注入上下文；`PreToolUse` 支持返回 `{"decision": "block", "reason": "..."}` 实施确定性行为拦截；`PostToolUse` 能精确捕获文件写入后的哈希与命令输出。
  - **Transcript：** 本地自动写入完整 JSONL，包含精确的 turn 结构与工具调用输入输出。
- **Codex `[CODE][DOC]` (CLI/Extension):**
  - **Hooks 限制：** 仅支持 4 个基础事件（主要为 `SessionStart`, `UserPromptSubmit`, `Stop`），**完全缺失 `PreToolUse` 与 `PostToolUse`**。
  - **队列与稳定性限制：** 官方插件不具备磁盘持久化队列，若外部服务未响应直接静默超时。
  - **补偿措施：** SagaContext 在 Codex 侧必须退化为**“基于 Stop 后的异步 Transcript 增量补偿”**；无法实现实时 PreToolUse 规则阻断，改为在 `UserPromptSubmit` 进行前置安全规则提示。

#### 2. 异常退出与事务补偿（WAL & Graceful Recovery）
宿主进程被 `kill -9`、断电或窗口崩溃时，无法保证收到 `SessionEnd` 或 `Stop` 事件。
- **设计对策：** 策略层 daemon 监听宿主事件时，在每一次 `UserPromptSubmit` 及检测到输入时，将增量事件流水即时写入本地 SQLite WAL 数据库。
- **孤儿会话恢复（Crash Recovery Probe）：** 当下一次任何会话触发 `SessionStart` 或 daemon 定时扫描时，检查所有状态处于 `in_progress` 但最后心跳超过 30 分钟的“孤儿会话”，自动触发针对未结算 transcript 的增量补偿对账，避免记忆丢失。

### R5 · P1：什么才是值得实现的个性化策略？

#### 1. 个性化四个维度的收益排序
1. **个性化上下文召回（Recall Policy，P0 级最高收益）：** 动态计算 Token 预算。在 `SessionStart` 阶段压制通用细节，优先注入当前 Repo 的核心约束与活跃任务；在代码编写阶段按命中文件路径精准注入坑点与规则。
2. **个性化执行与阻断（Compliance Enforcement，P1 级高收益）：** 将习惯与偏好转为确定性的校验命令与正则，避免无效的上下文“祈祷式提示”。
3. **个性化内容演化（Evolution Policy，P1 级持久收益）：** 支持技术品味的渐进式调整与自动过期。
4. **个性化在线学习微调（Online RL/Weight Learning，P2 级低性价比）：** 样本稀疏，极易过拟合，暂缓在线微调。

#### 2. 首版可解释静态层叠策略（Static Tiered Policy）
冷启动与生产初期摒弃黑盒打分，采用完全确定性的打分与预算裁剪公式：
$$\text{RankScore}(m) = S_{\text{semantic}}(m) \times W_{\text{scope}} \times W_{\text{type}} \times \text{Decay}(\Delta t)$$
- **作用域权重 $W_{\text{scope}}$：** `path_exact` ($1.5$) $>$ `repo_current` ($1.2$) $>$ `global` ($0.8$)。非当前项目的记录直接硬过滤（权重为 0）。
- **知识类型权重 $W_{\text{type}}$：** `convention` ($1.3$, 硬性规则) $>$ `gotcha` ($1.2$, 涉及当前变更文件) $>$ `decision` ($1.0$) $>$ `profile` ($0.7$)。
- **时间衰减 $\text{Decay}(\Delta t)$：** 半衰期设定为 90 天，公式为 $0.5^{\Delta t / 90}$，但若其被标记为 `immutable` 或由显式用户指令建立，则不衰减。
- **预算硬分配（Tokens）：** 
  - `SessionStart`：总计上限 2000 Tokens（L4 任务 400 + L2 约定 800 + L3 架构与坑 600 + L1 用户画像 200）。
  - `UserPromptSubmit`：总计上限 600 Tokens（按 Prompt 语义召回 Top-3 针对性经验）。

### R6 · P1：怎样证明我们比直接用现有记忆系统更好？

#### 1. 评测基准定位与缺陷纠偏
- **LongMemEval-V2 领域错配纠正：** 严格遵循审核意见结论，LongMemEval-V2 的轨迹主体是 Web-Agent 与企业通用工作流，并非软件工程。
- **推荐测试基准矩阵：**
  - **MemoryCode 基准：** 评估 Coding 多会话长程记忆、无显式提示下规则自发遵守率（Prospective Memory）。
  - **LongMemCode 基准：** 针对真实多语言代码库的大规模上下文检索确定性基准（AST Ground Truth）。
  - **Saga-Coding-Fixture（自建场景集）：** 录制 50 条基于真实的 Claude Code / Codex 重构、Bugfix 交互轨迹，人工标注事实建立、演化更新、反转与跨库隔离事件。

#### 2. 五类对照组消融实验设计
在完全固定的基准数据集与相同的宿主执行环境下对比：
1. **Group 0 (No Memory)：** 裸宿主，每次纯无记忆冷启动。
2. **Group 1 (Host Native)：** 启用 Claude Code Auto Memory (`MEMORY.md`) / Codex 原生记忆。
3. **Group 2 (Raw Backend)：** 裸 OpenViking 或裸 Mem0（仅依赖其自带的 auto-extract 与 auto-recall）。
4. **Group 3 (SagaContext Static)：** SagaContext 静态规则路由 + 锚定对账 + 强证据账本（无在线学习）。
5. **Group 4 (SagaContext Adaptive)：** SagaContext 在静态基础上开启动态使用反馈（`used` 信号调权）。

#### 3. 核心定量评测指标公式
- **过时事实更新率（Supersede Accuracy, SA）：** 当项目事实发生变更时，下一会话输出采用新事实且不输出旧事实的比例：
  $$\text{SA} = \frac{\sum \mathbb{I}(\text{Output contains } F_{\text{new}} \land \text{Output strictly excludes } F_{\text{old}})}{N_{\text{update\_cases}}}$$
- **跨项目污染率（Cross-Repo Pollution Rate, CRP）：** 在项目 B 中误注入或输出了项目 A 专属约定的比例（目标必须为 0%）：
  $$\text{CRP} = \frac{N_{\text{wrong\_scope\_injected}}}{N_{\text{total\_injections}}}$$
- **证据可回溯率（Provenance Grounding Rate, PGR）：** 注入记忆能够无歧义定位到具体 `(session_id, turn_id, git_commit)` 的比例（目标 $\ge 98\%$）。
- **Token 开销比（Token Overhead Ratio, TOR）：** 记忆对账提取与上下文注入消耗的 Token 总量与任务本体消耗的比值（目标 $\le 3.5\%$）。

```text

     - 锚点集 A 为空 (新问题)。Reconciler 判定: `status=NEW`。
  4. 写入操作:
     - 写入记忆: URI = `viking://.../dev_gotcha/grpc_health_probe_fix.md`
```

## 5. 最小模型与中立接口草案（Backend SPI）

### 5.1 统一记忆记录模型（Canonical Memory Model）
```python
from pydantic import BaseModel, Field
from typing import Literal, Optional, List, Dict, Any

class GroundingEvidence(BaseModel):
    session_id: str
    turn_index: int
    source_host: Literal["claude-code", "codex", "generic"]
    git_root: Optional[str] = None
    git_rev: Optional[str] = None
    tool_call_id: Optional[str] = None
    verified_success: bool = False
    quote: str

class CanonicalMemory(BaseModel):
    id: str = Field(description="全局稳定 UUID / Hash")
    layer: Literal["user", "preference", "project", "task", "team", "experience"]
    content_type: Literal["profile", "taste", "convention", "decision", "project_map", "gotcha", "task"]
    scope_key: str = Field(description="global | repo:<hash> | path:<hash>:<glob>")
    body_text: str = Field(description="供 LLM 阅读的结构化 Markdown 或纯文本")
    structured_payload: Dict[str, Any] = Field(description="类型专属强模式字段")
    
    # 演化与证据
    version: int = 1
    status: Literal["active", "superseded", "pending_confirm", "retired"] = "active"
    superseded_by: Optional[str] = None
    confidence: float = Field(ge=0.0, le=1.0, default=0.8)
    evidence_ledger: List[GroundingEvidence] = []
    
    created_at: str
    updated_at: str
```

### 5.2 后端中立接口（MemoryBackendSPI）
所有适配器（OpenViking, Mem0, In-Memory Fixture）必须严格实现的公共接口：

```python
from abc import ABC, abstractmethod
from typing import List, Optional, Dict, Any

class MemoryBackendSPI(ABC):
    @abstractmethod
    async def initialize(self, config: Dict[str, Any]) -> None:
        """初始化连接池或本地客户端"""
        pass

    @abstractmethod
    async def get_by_id(self, memory_id: str) -> Optional[CanonicalMemory]:
        """按稳定 ID 精确拉取单一权威实体"""
        pass

    @abstractmethod
    async def search(
        self,
        query: str,
        scope_keys: List[str],
        layers: Optional[List[str]] = None,
        top_k: int = 10,
        min_score: float = 0.5
    ) -> List[CanonicalMemory]:
        """按 Query 与 Scope 约束执行密集/稀疏混合检索"""
        pass

    @abstractmethod
    async def write_atomic(self, memory: CanonicalMemory, expected_version: Optional[int]) -> bool:
        """带版本 CAS 约束的写入。若 expected_version 冲突则返回 False，由策略层重试"""
        pass

    @abstractmethod
    async def mark_superseded(self, old_id: str, new_id: str) -> bool:
        """原子标记废弃并链向新记录"""
        pass

    @abstractmethod
    async def delete(self, memory_id: str, hard_delete: bool = False) -> bool:
        """软删除或物理清理"""
        pass
```

## 8. 调研结论与下一步行动计划

### 8.1 调研核心结论
1. **策略层完全可以独立立足：** 现有记忆后端（OpenViking / Mem0）在底层基础设施（混合检索、向量构建、分层存储）表现优秀，但在**“开发者特定画像”、“强证据链溯源”、“旧知识锚定增量对账”、“跨仓库作用域安全”**四个维度存在明显的系统性缺失。SagaContext 填补的正是这层关键策略空白。
2. **拒绝“换皮式包装”：** SagaContext 绝不应做成“又一个把提示词包装后调用 OpenViking 的壳”，而是必须坚持**本地轻量权威账本 + 跨后端中立 SPI**，以可验证的测试用例和消融基准确立其独立技术价值。

### 8.2 立即执行的下一步行动（M0 / M1 准入）
1. **冻结设计规格：** 根据本调研结论，将 `04-设计规格-v0.2.md` 吸收的技术决策（本地 SQLite WAL、Mem0 SPI 兼容性、正交分层模型）正式升级为 `v0.3` 并完成冻结。
2. **建立 Backend 契约测试集：** 实现 `MemoryBackendSPI` 与针对 OpenViking 及 Mem0 的适配器，跑通 T01–T12 的基础功能断言。
3. **闭环 Coding 偏好与项目记忆评测：** 搭建基于 `MemoryCode` 范式的离线回放 Runner，正式产生第一组带标注的对比基准数据。
